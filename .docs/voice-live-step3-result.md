# Step 3 구현 결과: 주기적 재변환 오케스트레이터 (`live_transcribe.py`)

> `.docs/voice-live-step3-detailed.md`(개념 가이드)를 따라 구현하고 실제
> 백그라운드 실행으로 검증한 결과 기록. 코드는 `live_transcribe.py` 참고.

## ✅ 한 줄 요약

마이크를 계속 녹음하면서 N초마다 누적 버퍼 전체를 Whisper에 재변환하고,
`printed_until` 기준으로 새 세그먼트만 출력/파일 저장하는 `live_transcribe.py`를
구현했다. 실제로 11사이클(~76초) 백그라운드 실행하여 주기적 재변환, 파일
갱신, `printed_until` 중복 방지 로직, 그리고 비정상 종료 시 데이터 보존까지
확인했다.

## 🛠️ 가이드 대비 구현 시 확인/조정한 것

### 1. numpy 배열 직접 입력은 실제로 지원되지만, **샘플레이트를 스스로 맞춰야 한다**

가이드 문서는 "설치된 버전에서 배열 입력이 되는지 실제로 검증할 것"을
명시했다. 검증 결과:

```python
model.transcribe(buffer.flatten(), language="ko", vad_filter=True)  # ✅ 정상 동작, TypeError 없음
```

**작동은 하지만 발견한 함정**: `WhisperModel.transcribe()`는 배열을 받을 때
**그 배열이 16000Hz라고 그냥 가정**하고, 별도로 리샘플링하지 않는다. 검증 삼아
Step 2의 22050Hz 합성 오디오 배열을 그대로 넣어봤더니:

```
[파일 경로로 직접 전달 시 (22050Hz, 올바르게 디코딩됨)]
[00:00:00.000 -> 00:00:04.960] 환자는 50대 남성이며 교통사고로 흉부 충격을 받았습니다.

[같은 오디오를 22050Hz 배열째로 transcribe()에 직접 전달 시]
[00:00:00.000 -> 00:00:06.880] 환자는 50대 남성이며 교통사고로 흉부 충격을 받았습니다.
```

문장은 똑같이 인식되지만 **세그먼트 종료 시각이 다르다** (4.960초 vs
6.880초, 비율 1.387 ≈ 22050/16000 = 1.378). 파일 경로로 넘기면 내부적으로
ffmpeg/av가 정확히 리샘플링하지만, 배열로 직접 넘기면 그 과정이 생략되어
"배열의 샘플 개수를 16000Hz 기준으로 해석"해버려 타이밍이 늘어난 것으로
추정된다.

**이 프로젝트에서는 문제가 되지 않는 이유**: `MicRecorder`가 애초에
`sample_rate=16000`으로 고정 캡처하므로, `live_transcribe.py`가 넘기는
`buffer.flatten()`은 항상 진짜 16000Hz다. 폴백(임시 WAV 저장 후 경로 전달)
분기는 구현했지만 이번 테스트에서는 필요하지 않았다 — 배열 입력이 정상
동작해 폴백 코드 경로는 타지 않았다.

**교훈**: 이후 이 함수를 다른 샘플레이트의 오디오 소스와 함께 재사용할
일이 생기면, 배열을 넘기기 전에 반드시 16000Hz로 리샘플링해야 한다.

### 2. `nohup python live_transcribe.py &`로 백그라운드 실행 시 출력 버�를 주의

첫 시도에서 `nohup python live_transcribe.py ... > log.txt 2>&1 &`로 실행했더니
30초 넘게 로그 파일이 완전히 비어 있었다. 원인은 Python이 stdout이 터미널이
아닌 파일로 리다이렉트되면 **자동으로 라인 버퍼링 대신 블록 버퍼링으로
전환**하기 때문 — `print()`가 즉시 flush되지 않고 내부 버퍼가 찰 때까지
쌓인다. `python -u`(unbuffered) 옵션으로 재실행하니 정상적으로 실시간
로그가 찍혔다. 실제 사용자가 터미널에서 직접 실행할 때는 해당하지 않는
문제이지만(터미널은 라인 버퍼링), 백그라운드/파이프 실행 시에는 알아둘
필요가 있다.

## 🔍 발견 사항 1: VAD가 정적/생활 소음에서 짧은 오탐(false positive)을 만든다

발화 없이 조용한 방에서 실행했음에도 1차, 6차 사이클에서 `하하하하`라는
텍스트가 인식되었다. 이는 사람 음성이 아니라 컴퓨터 팬 소음, 미세한 배경
잡음 등을 `vad_filter=True`가 "음성 활동"으로 오판하고, Whisper 모델이
그 짧은 구간을 그럴듯한 한국어 음절로 환각(hallucination)한 결과로 보인다.

**실서비스 관점에서 중요한 시사점**: VAD + 경량 Whisper 모델(`base`) 조합은
무음 구간에서도 드물게 오탐을 만들어낼 수 있다. 실제 응급 통화 환경(더
큰 배경 소음)에서는 이 빈도가 더 높아질 수 있으므로, Step 4의
`MedicalRelevanceFilter`가 이런 무의미한 오탐을 걸러내는 데 실질적으로
기여할 것으로 예상된다("하하하하"는 의료 관련 앵커 문장과 유사도가
낮을 것이므로 필터링 단계에서 "제외" 판정될 가능성이 높다).

## 🔍 발견 사항 2: `printed_until` 중복 방지 로직의 한계를 실제로 목격

1차와 6차 모두 세그먼트 시작 시각이 `00:00:00.000`으로 동일하게 출력되었다.
언뜻 "중복 출력 버그"처럼 보이지만, 코드를 다시 확인하면 의도된 동작이다:

- 1차 사이클(누적 4.9초)에서 Whisper가 `[0.0 → 약 1~2초]` 구간을 "하하하하"로
  판정 → `printed_until`이 그 `seg.end` 값으로 갱신됨.
- 6차 사이클(누적 39.2초)은 **버퍼 전체(0~39.2초)를 처음부터 다시
  재변환**한다. 이번에는 VAD가 앞부분을 다르게 잘라, `seg.start`는 여전히
  `0.0`이지만 `seg.end`가 이전 `printed_until`보다 **더 뒤**로 판정되었다.
  `seg.end > printed_until` 조건을 만족하므로 "새 세그먼트"로 재출력된다.

가이드 문서(`voice-live-step3-detailed.md`)에 이미 경고되어 있던 바로 그
현상("VAD 재판정으로 경계가 살짝 흔들려 드물게 한두 단어가 겹쳐 보일 수
있음 — 이번 단계에서는 허용 오차로 남겨둔다")을 실제 실행에서 확인한
것이다. 완벽한 스트리밍 diff(단어 단위 정합)는 이번 단계 범위 밖이라는
가이드의 판단이 실제로 타당함을 재확인했다.

## 🔍 발견 사항 3: 비정상 종료(강제 kill)에도 데이터가 보존됨

이 자동화된 테스트 환경에서는 실제 터미널의 Ctrl+C(SIGINT)를 프로세스에
전달할 수 없어(백그라운드로 격리된 실행 환경의 제약), `finally` 블록의
"최종 세션 요약" 출력 경로까지는 확인하지 못하고 `kill -9`로 강제
종료했다. 그럼에도:

```bash
$ cat data/live_text/live_test1.txt
하하하하 하하하하
```

**11차 사이클(마지막으로 실행 완료된 사이클)까지의 내용이 정확히
보존되어 있었다** — 매 사이클마다 `out_path.write_text()`로 즉시 디스크에
쓰는 설계 덕분에, 프로그램이 어느 시점에 죽더라도 마지막으로 완료된
사이클까지의 텍스트는 손실 없이 남는다. 이는 실제 응급 통화 환경에서
비정상 종료(네트워크 단절, 프로세스 크래시 등)가 발생해도 그때까지의
통화 내용을 잃지 않는다는 뜻이라 중요한 특성이다.

`finally` 블록의 세션 요약 출력 자체(코드 상 존재하는 정상 Ctrl+C 경로)는
실제 대화형 터미널에서 사용자가 직접 Ctrl+C를 눌러야 확인 가능하며, 코드
검토로는 로직이 올바름을 확인했다(`KeyboardInterrupt` 캐치 → `recorder.stop()`
→ 누적 텍스트가 있으면 요약 출력).
