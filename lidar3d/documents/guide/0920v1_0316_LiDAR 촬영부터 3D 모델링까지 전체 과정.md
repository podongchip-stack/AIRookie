## 0. 한 장 요약

```
[아이폰]                    [맥]                          [A100 GPU]
LiDAR + 카메라              업로드 수신                    3DGS 학습
  ↓                           ↓                              ↓
원자료 6종 기록        ─→   융합 · 사람 검출          ─→   사람별 3DGS
  (변환하지 않음)             (3D 재구성)                   (사진 같은 3D)
                              ↓                              ↓
                           3D 뷰어 ←─────────────────────────┘
```

**핵심 원칙: 앱은 재구성하지 않는다.** 아이폰은 센서가 준 값을 그대로 기록만 하고,
3D 재구성은 전부 맥에서 한다. 이유는 세 가지다.

1. 폰에서 무거운 연산을 하면 발열로 **ARKit 트래킹 자체가 나빠진다**
2. 원자료가 남아 있으면 융합 파라미터를 바꿔가며 **몇 번이든 다시 만들 수 있다**
3. Android로 이식할 때 **폰이 하는 일이 적을수록 옮기기 쉽다**

## 1. 촬영 — 아이폰이 기록하는 것

`ARWorldTrackingConfiguration`으로 ARSession을 돌리며 **한 콜백 안에서** 모두 기록한다.
한 곳에서 처리해야 `frame_index`가 정확히 맞물린다 — 이게 나중의 모든 계산의 전제다.

### 1-1. 기록되는 6종

| 파일 | 내용 | 규격 (실측) |
|---|---|---|
| `video.mov` | RGB 영상 | **1920×1440**, 527프레임 |
| `depth/depth_*.bin` | LiDAR 깊이 | **256×192** Float32, 미터, 352장 |
| `depth/conf_*.bin` | 신뢰도 | 256×192 UInt8 (0/1/2) |
| `arkit_pose.csv` | 카메라 위치·방향·내부파라미터 | 프레임마다 1행 |
| `scene_mesh.ply` | ARKit이 실시간 생성한 메시 | 81,940정점 / 133,502면 |
| `scene_mesh_faces_class.bin` | 면별 분류 라벨 | 면마다 1바이트 |

보조로 `imu.csv`, `device_motion.csv`, `coaching.csv`, `metadata.json`(87키)가 함께 남는다.

### 1-2. 좌표계

ARKit world 좌표계를 **그대로** 쓴다. 오른손 좌표계, **Y가 위**(중력 정렬), 단위는 **미터**,
카메라는 **-Z 방향**을 본다. `camera.transform`은 **camera-to-world**다.

> **앱은 좌표를 변환하지 않는다.** 변환은 손실과 버그의 원인이고, 원본이 남아 있으면
> 나중에 어떤 규약으로든 바꿀 수 있다. COLMAP 변환도 맥에서 한다(3-2 참조).

### 1-3. `arkit_pose.csv` 스키마

```
frame_index,timestamp,tx,ty,tz,qx,qy,qz,qw,tracking_state,tracking_state_reason,fx,fy,cx,cy
```

- `tracking_state` — 0=notAvailable, 1=limited, 2=normal. **2가 아닌 구간은 이후 전부 버린다**
- `fx,fy,cx,cy` — 카메라 내부파라미터. **프레임마다 미세하게 달라서** 매 행에 기록한다
  (실측: 732행이 전부 서로 다른 값이었다)

### 1-4. 영상에 회전 변환을 붙이지 않는 이유

`AVAssetWriterInputPixelBufferAdaptor`에 `frame.capturedImage`를 그대로 넣는다.
보기 좋으라고 회전을 붙이면 **영상 픽셀과 `fx,fy,cx,cy`가 어긋나** 모든 투영 계산이 틀어진다.
그래서 영상은 센서 원본 방향 그대로 눕혀서 저장된다 — 의도된 것이다.

### 1-5. 촬영 시 알아야 할 실측 한계

| 항목 | 실측값 | 의미 |
|---|---|---|
| LiDAR 유효 반경 | **약 2.5m** | 사양의 5m가 아니다. 멀리 있는 것은 안 잡힌다 |
| 한 번 촬영 커버리지 | 최대 **18.7%** | 한 바퀴 돌아도 대부분은 "안 본 곳"이다 |
| ARKit 메시 격자 | **3cm 고정** | 부위별로 조절하는 API가 없다 |
| 빈 공간 | **"없음"이 아니라 "안 봄"** | 판단 근거로 쓰면 안 된다 |

## 2. 전송 — 아이폰에서 맥으로

```
POST /session/start            세션 폴더 생성
POST /session/upload           파일별 업로드 (50MB 이하)
POST /session/upload/chunk     50MB 초과 시 20MB씩 조각 전송
POST /session/upload/complete  조각을 원본으로 합침 (크기 대조)
POST /session/stop             완료 신호 → 3DGS 자동 처리 큐에 등록
```

### 왜 분할 전송이 필요한가

**Cloudflare 무료 플랜의 요청 본문 상한이 100MB**인데 `video.mov`가 135MB까지 나온다.
통째로 보내면 Cloudflare 단계에서 잘려 **서버에 요청이 도달조차 하지 않는다**
(앱에는 "The request timed out"으로만 보이고 서버 로그엔 아무것도 안 남는다).

**전송만 조각낸다.** 서버가 원래 이름으로 다시 합치므로 세션 폴더 구조도
`frame_index` 대응도 바뀌지 않는다.

### 접속 경로 두 가지

| 상황 | 주소 | 비고 |
|---|---|---|
| 같은 Wi-Fi | `http://192.168.x.x:8000` | 공유기 안에서만 오감 |
| 다른 망 (셀룰러) | `https://lidar.rookie-goldenlink.xyz` | Cloudflare Tunnel 경유 |

**실측 (아이폰 12 Pro → 셀룰러 → Cloudflare → 맥)**

세션 파일의 도착 시각으로 잰 값이다:

```
합계 104.4 MB  /  15~17초  =  약 6~7 MB/s

video.mov (78MB)   +0초   ← 분할 전송
작은 CSV들          +1초
scene_mesh.ply      +4초
metadata.json       +5초
depth.zip (21MB)   +15초  ← 마지막
```

Cloudflare 자체는 병목이 아니다. 캐시 없이 통과시키기만 한다
(`cf-cache-status: DYNAMIC` 실측 확인).

> ⚠️ **셀룰러 속도는 환경에 따라 수십 배로 흔들린다.** 위 6~7 MB/s는 한산한 곳의 값이다.
>
> | 조건 | 업로드 | 104MB 소요 |
> |---|---|---|
> | 5G 양호 | 20~50 MB/s | 2~5초 |
> | **실측(한산)** | **6~7 MB/s** | **15~17초** |
> | LTE 보통 | 1~3 MB/s | 35~100초 |
> | **혼잡한 행사장** | 0.1~0.5 MB/s | **3~15분** |
>
> 마지막 줄이 부스 시연의 진짜 위험이다. 수백 명이 같은 기지국을 쓰면 급격히 느려지고
> 코드로는 어쩔 수 없다. **가능하면 촬영 폰과 맥을 같은 망(휴대용 공유기 등)에 두는 편이
> 안전하다.** 터널 경로는 그때도 뷰어 공개용으로 남겨 둔다.

## 3. 재구성 — 맥에서 3D 만들기

### 3-1. 세 가지 메시, 각각 다른 용도

| 산출물 | 만드는 법 | 특징 |
|---|---|---|
| `scene_mesh.ply` | 폰이 실시간 생성 | 즉시 사용 가능, 3cm 격자로 거침 |
| `fused_mesh.ply` | `fuse_depth.py` — 뎁스 TSDF 융합 | 균일 정밀, 무겁다 |
| `fused_adaptive.ply` | `stage1_masks.py` + `stage2_fuse.py` | **배경 4cm / 사람 1cm** |

**적응형이 핵심이다.** 균일 1cm 대비 **정점 19배 감소, 8.3배 빠름**인데
사람 디테일은 동일했다. 배경은 거칠어도 되고 사람만 정밀하면 되기 때문이다.

### 3-2. 왜 2단계로 나누는가

> `torch`(YOLO)와 `open3d`(TSDF)를 **한 프로세스에서 import하면 이 환경에서 멈춘다**
> (CPU 0%로 대기 상태, 실측 확인). 그래서 별도 프로세스로 분리했다.
> 부수 효과로 마스크가 파일로 남아 **융합 파라미터를 바꿔 여러 번 실험**할 수 있다.

**1단계 `stage1_masks.py`** — YOLO-seg로 사람을 픽셀 단위로 분리 → `person_masks.npz`

bbox가 아니라 **세그멘테이션**을 쓴다. bbox를 쓰면 사각형 안의 벽과 바닥까지 통째로
사람으로 잡혀서, "사람"이 4.6×1.3×2.4m 띠 모양으로 나온 적이 있다.

설정은 실측으로 정했다 (표본 40프레임):

| 설정 | 사람 검출 프레임 | 총 인원 |
|---|---|---|
| n-seg @640 conf.35 (예전) | 12/40 | 16 |
| **l-seg @640 conf.15 (현재)** | **22/40** | 34 |
| m-seg @1280 | 14/40 | 20 ← **해상도를 올리면 오히려 나빠진다** |

사람이 0.87m 거리에서 화면을 가득 채워서, 1280으로 넣으면 YOLO가 학습한 크기 분포를
벗어난다. **`imgsz`는 640을 유지할 것.**

**2단계 `stage2_fuse.py`** — 뎁스 + 포즈로 TSDF 융합, 사람만 1cm 복셀

> ⚠️ `window`(시간창)는 **0 = 제한 없음**이어야 한다. "첫 사람이 보인 시각부터 N초"라서
> 사람들이 촬영 내내 등장하면 대부분이 잘린다.
> 실측: `window 3.0` → 객체 10프레임 / **사람 1명**, `window 0.0` → 430프레임 / **사람 9명**

### 3-3. 사람별로 분리하기

융합된 객체 메시를 연결 덩어리로 나눈 뒤 크기로 거른다.
움직임으로 생긴 겹침(ghosting)이 배경과 뭉친 덩어리는 여기서 걸러지고,
**조용히 버리지 않고 `persons.json`의 `rejected`에 이유와 함께 남긴다.**

결과: `fused_person_01.ply` … + `persons.json`(중심 좌표·크기·표면적)

### 3-4. 실사 색 입히기

`color_mesh.py`가 영상 프레임에서 실제 색을 가져와 정점에 칠한다.

> **한 번도 관측되지 않은 곳은 회색으로 남긴다.** 안 본 곳의 색을 지어내지 않는다 —
> 부상자 판단에 쓰일 수 있는 데이터에 추측을 섞으면 안 된다.

## 4. 3DGS — 사진 같은 3D

메시는 표면을 삼각형으로 근사해서 안경테·손가락 마디·옷 주름을 잃는다.
3D Gaussian Splatting은 **반투명 타원체 수백만 개**로 장면을 표현해 사진에 가까워진다.

### 4-1. "학습"이 무엇을 하는가

신경망을 학습시키는 게 아니다. **이 장면 하나를 재현하도록 타원체를 맞추는 최적화**다.
가우시안 하나가 62개 숫자를 갖는다:

| 속성 | 개수 | 의미 |
|---|---|---|
| `x,y,z` | 3 | 위치 |
| `rot_0~3` | 4 | 회전 |
| `scale_0~2` | 3 | 세 축 크기 |
| `opacity` | 1 | 불투명도 |
| `f_dc`, `f_rest` | 48 | 색 (보는 각도에 따른 변화 포함) |

반복 한 번 = 사진 한 장 고름 → 그 카메라 위치에서 렌더 → 실제 사진과 비교 →
차이를 줄이는 방향으로 62개 숫자 수정. 이걸 30,000번 돌린다.

### 4-2. COLMAP SfM을 건너뛴다 — 가장 큰 이점

보통 3DGS는 사진에서 카메라 위치를 역산(SfM)해야 하는데, 우리는 **ARKit이 준
미터 단위 절대 포즈**가 이미 있다. `export_colmap.py`가 변환만 한다:

```
R_c = FLIP @ R.T,  t_c = -R_c @ t,  FLIP = diag([1,-1,-1])
```
(ARKit: camera-to-world, -Z 전방 / COLMAP: world-to-camera, +Z 전방)

**검증 방법**: 초기 점군을 카메라로 재투영해 LiDAR 깊이와 대조한다.
실측 중앙오차 **+1.3cm** — 변환이 정확하다는 뜻이다.

### 4-3. A100에서만 되는 이유

3DGS 래스터화가 **CUDA 전용 커널**이라 맥의 MPS에는 구현 자체가 없다.

| 단계 | 소요 (실측) |
|---|---|
| COLMAP 내보내기 (527프레임) | ~1분 |
| A100 업로드 (163MB) | ~15초 |
| **학습 30,000스텝** | **17분** |
| 크롭 + 다운로드 | ~30초 |

결과: 가우시안 **1,422,412개**, L1 오차 0.281 → 0.024

### 4-4. 반복을 늘려도 입체감은 안 늘어난다

| 스텝 | 경과 | L1 |
|---|---|---|
| 2,500 | 1.2분 | 0.0523 |
| 17,500 | 9.8분 | 0.0159 ← 가우시안 증식은 여기서 멈춤 |
| 29,500 | 16.9분 | 0.0297 |

**학습은 정보를 만들어내지 않는다.** 앞모습만 찍혔으면 몇 만 스텝을 돌려도 뒷모습은 없다.
입체감을 좌우하는 것은 순서대로:

1. **시점 각도 수** — 사람 주위를 얼마나 돌았는가
2. **대상이 정지해 있었는가** — 3DGS는 정지 장면을 가정한다. 움직이면 번진다
3. 입력 해상도 (`--factor`)
4. 반복 횟수 ← 가장 작다

### 4-5. 3DGS는 보기 전용

반투명 점 분포라 **표면이 없다.** 거리·크기 측정은 반드시 메트릭 메시로 해야 한다.
그래서 뷰어에서 메시를 대체하지 않고 토글로 **추가**했다.

## 5. 자동화 — 업로드하면 알아서 돈다

`/session/stop`이 `server/gs_job.py`의 큐에 등록하면 다음이 순서대로 실행된다:

```
적응형 융합 → COLMAP 내보내기 → GPU 업로드 → 학습 → 크롭 → 다운로드
```

진행 상황은 `gs_status.json`에 기록되고, 뷰어가 버튼에 표시한다:

```
3DGS 대기 중… → 3DGS 학습 중 62% → 3DGS로 보기
```

**세 가지 안전장치**

1. **선택적 단계** — `LIDAR_GPU_HOST`가 없거나 GPU가 죽어도 업로드·메시·사람 검출은 정상
   (대회 GPU는 **2026-11-05 17:00에 회수**된다 — 그때 이 경로는 반드시 죽는다)
2. **기다리지 않는다** — 학습 17분 동안 `/session/stop`이 타임아웃되면 앱에는
   "업로드 실패"로 뜬다. 실제로는 다 올라갔는데도
3. **한 번에 하나만** — GPU가 하나뿐이라 동시 학습은 경합한다

## 6. 보기 — 3D 뷰어

`server/viewer/index.html` 하나로 된 정적 페이지(three.js r160).

- 메시 소스 전환 (ARKit / 직접 융합 / 적응형 / 사람만)
- 분류별 색상 범례 + On/Off
- 두 점 클릭 거리 측정 (미터)
- 검출된 사람 목록 → 클릭하면 **모달**에 개별 3D + 참조 사진
- 모달에서 **메시 ↔ 3DGS** 전환

### 3DGS 렌더링에서 반드시 지켜야 할 두 가지

```js
gsViewer = new GS3D.DropInViewer({
  gpuAcceleratedSort: false,      // true면 아무것도 안 그려진다 (실측: 0% vs 15.37%)
  sharedMemoryForWorkers: false,  // COOP/COEP 헤더가 없으므로
});
await gsViewer.addSplatScenes([{
  path: withToken(...),
  format: GS3D.SceneFormat.Ply,   // ?token= 때문에 확장자 판별이 실패한다
}], false);
```

둘 다 **오류 없이 검은 화면만** 나오는 종류라 원인을 찾기 매우 어려웠다.

## 7. 전체 소요 시간 (실측)

| 단계 | 소요 |
|---|---|
| 촬영 | 20~40초 |
| 업로드 (104MB, 셀룰러→터널) | **15~17초** (한산한 환경 실측) |
| 적응형 융합 (YOLO 198프레임 + 3D) | **100초** |
| 3DGS (내보내기 → 학습 → 다운로드) | **약 19분** |
| **합계** | **약 21분** |

부스 운영에는 3DGS가 너무 느리다. 시민에게는 **즉시 나오는 ARKit 메시**를 보여주고,
3DGS는 미리 만들어 둔 것을 전시하는 편이 현실적이다.
(`LIDAR_GPU_ITERS=3000`으로 낮추면 학습이 1.5분이 되어 전체 5분까지 줄일 수 있다)

## 9. 이 문서의 한계

- 수치는 특정 세션 실측이라 환경이 바뀌면 달라진다
- `merge_sessions.py`(다중 기기 병합)와 골든링크 연동은 여기서 다루지 않았다
  — 각각 `documents/design/` 참조
- 자동화(5장)는 각 단계를 손으로 검증했으나 **연쇄 전체를 끝까지 돌려본 적은 없다**
- 업로드 속도는 **세션 파일의 도착 시각 차이**로 잰 것이라, 앱이 파일을 준비하는 시간이
  섞여 있을 수 있다. 정확한 전송 속도만 보려면 앱 쪽 계측이 필요하다
