# 골든링크 통합 대비 — LiDAR_3D 설계 검토

**작성 2026-09-18 22:51 · v1**
**대상: 골든링크 통합 설계 결정자 + LiDAR_3D 담당**

LiDAR_3D를 골든링크(voice / info / hub / dashboard)의 **향후 입력 채널**로 붙일 때,
지금 구조에서 무엇을 바꿔야 하는지 판단한 결과.

> **현재 작업 범위는 "캡처 품질 검증"까지이며 hub 연동은 범위 밖이다.**
> 이 문서는 나중에 스키마를 갈아엎지 않기 위해 **지금 확정해둘 것**만 정리한다.

---

## 0. 판단 요약

| 항목 | 판단 | 근거 |
|---|---|---|
| **caseId 필드** | 🔴 **지금 넣어야 함** | 없으면 이미 찍은 세션이 사건에 못 붙는다 |
| **전송 구조 (별도 스토리지 + 참조 URL)** | 🟢 **이미 만족** | hub를 경유하지 않는 구조가 이미 구현돼 있다 |
| **파일 목록 관리** | 🟡 **단일화 권장** | 지금도 2중 관리, 통합 시 5중이 된다 |
| **순위 비관여** | 🟢 **접점 없음** | 다만 대시보드 임베드 시 주의사항 있음 |

| 보관 정책 | **없음** |

## 2. caseId — 지금 넣어야 하는 이유

### 문제

현재 두 대로 찍은 세션은 **촬영 시각이 20초 차이라는 것만으로** 같은 사건임을 추정한다.
동시다발 사건에서는 이 방식이 깨진다.

```
session_20260918v1_iPhone15Pro   01:42:11
session_20260918v1_iPhone12Pro   01:42:11   ← 시각이 가깝다는 것 외에 연결 고리가 없음
```

### 제안: `session_id`는 그대로, `case_id`를 별도 차원으로

```
session_20260918v1_iPhone15Pro  ─┐
session_20260918v1_iPhone12Pro  ─┼─ metadata.case_id = "CASE-2026-0918-0042"
merged_20260918T014500Z         ─┘
```

**`session_id`에 caseId를 넣지 않는 이유**

1. **1 사건 : N 세션**이다. 두 대원 + 재촬영 + 병합 결과가 하나의 caseId에 묶인다.
   폴더명에 넣으면 병합 결과 명명이 또 애매해진다.
2. **caseId가 촬영 시점에 없을 수 있다.** 먼저 찍고 나중에 배정되는 경우,
   폴더명 방식이면 이름을 바꿔야 한다 (= 이미 업로드된 파일 경로가 전부 깨진다).

### 구체 수정안

**앱 — `SessionManager.swift`**
```swift
@Published var caseId: String = ""          // UserDefaults에 유지 (두 대원이 각자 입력)

// metadata.json
"case_id":        caseId.isEmpty ? NSNull() : caseId,
"case_id_source": caseId.isEmpty ? NSNull() : "manual",   // 나중에 "hub" 추가
```
+ `ContentView`에 입력 필드 1개. 촬영 설정과 같은 방식으로 앱 재시작 후에도 유지.

**서버 — `app.py`**
```
POST /session/{id}/case     촬영 후 나중에 caseId를 붙이는 경로
GET  /cases/{caseId}        해당 사건의 모든 세션 반환
```

**병합 결과**도 원본 세션의 `case_id`를 상속한다.

## 3. 전송 구조 — 이미 요구사항을 만족

요구된 "hub를 거치지 않고 별도 스토리지에 올린 뒤 hub에는 참조 URL만" 구조는
**현재 이미 그렇게 동작한다.**

```
아이폰 ──HTTP 업로드──> LiDAR_3D 서버(= 스토리지) ──> 브라우저가 직접 열람
                              └─ hub는 이 경로에 없음
```

**근거:** 세션 1건이 126MB다. hub 경유는 애초에 불가능하다.

### 지금은 형태만 확정 (구현은 범위 밖)

voice의 `POST /voice/summary` 패턴을 그대로 따른다.

```json
POST {HUB}/3d/capture
{
  "caseId":     "CASE-2026-0918-0042",
  "sessionId":  "session_20260918v1_iPhone12Pro",
  "capturedAt": "2026-09-18T01:42:11Z",
  "viewerUrl":  "http://<3d-host>/viewer/?session=...&embed=1",
  "meshUrl":    "http://<3d-host>/session/.../file/scene_mesh.ply",
  "summary": {
    "extentMeters":    [9.0, 2.9, 6.5],
    "surfaceAreaM2":   107.9,
    "deviceModel":     "iPhone 12 Pro",
    "classFaceCounts": { "door": 10454, "window": 10309 }
  }
}
```

**설계 결정 3가지**

1. **`summary`에 숫자를 몇 개만 넣는다.**
   전체 87키 metadata를 보내면 hub 스키마가 3D 내부 구현에 결합된다.
   내부가 바뀔 때마다 스키마 4곳을 고쳐야 한다. **URL + 최소 요약만** 넘기고 상세는 뷰어에서 본다.
2. **`PUBLIC_BASE_URL` 설정값이 필요하다.**
   지금 서버는 `localhost` 기준이라 dashboard에서 열 수 없다. 대시보드가 닿는 호스트여야 한다.
3. ⚠️ **hub 스키마의 `extra` 설정을 먼저 확인할 것.**
   `ApprovalAction.reason`이 조용히 폐기된 것과 같은 사고가 난다.
   이 페이로드는 필드가 적어 위험이 작지만, 추가 전 확인을 전제로 한다.

## 4. 파일 목록 관리 — 실제 문제가 있는 지점

현재 허용 파일명이 **두 곳에 중복 정의**돼 있다.

| 위치 | 내용 |
|---|---|
| `server/app.py`의 `ALLOWED_FILENAMES` | 하드코딩된 set |
| 앱 `SessionManager.sessionFiles()` | 같은 목록을 Swift 배열로 |

지금도 2중인데 hub·dashboard까지 붙으면 **기존 "스키마 4중 수동 유지"가 5중이 된다.**

### 제안: 단일 출처 파일

`contracts/session_files.json`
```json
{
  "schema_version": 3,
  "files": [
    {"name":"scene_mesh.ply","required":true, "role":"model","exposeToHub":true},
    {"name":"metadata.json", "required":true, "role":"meta", "exposeToHub":true},
    {"name":"video.mov",     "required":false,"role":"raw",  "exposeToHub":false},
    {"name":"depth.zip",     "required":false,"role":"raw",  "exposeToHub":false}
  ]
}
```

- 서버가 이 파일에서 화이트리스트를 읽는다 (하드코딩 제거)
- `exposeToHub`가 hub에 URL을 넘길 파일을 결정한다 —
  **뎁스 29.6MB를 대시보드에 노출할 이유가 없다**
- Swift는 이 JSON을 런타임에 읽지 않으므로 앱은 목록을 유지하되,
  **CI에서 두 목록의 일치를 검사**하는 방식이 현실적이다

> caseId를 넣는 김에 같이 하는 것이 비용이 가장 적다. 나중에 하면 5곳을 동시에 고쳐야 한다.

## 5. 순위 비관여 — 현재 만족, 대시보드 임베드 시 주의

3D는 순위 계산과 **접점이 전혀 없다.**
`metadata.reconstruction_required`는 CAM 서버의 COLMAP 분기용이며 hub와 무관하다.

### 대시보드에 3D 패널을 붙일 때 지켜야 할 것

| 주의 | 이유 |
|---|---|
| **읽기 전용 모드 필요** (`/viewer/?session=X&embed=1`) | 현재 뷰어에는 병합 버튼·YOLO 패널·세션 드롭다운이 있다. **병원 화면에서 병합이 실행되면 안 된다** |
| **폴링 끄기** | 뷰어가 5초마다 `/sessions`를 폴링한다. 병원 화면이 열려 있는 동안 계속 요청이 간다 |
| **iframe 격리** | 3D 로드가 실패해도 대시보드가 깨지지 않아야 한다 ("3D 없어도 매칭 정상 동작") |
| **정렬 로직 미접촉** | 기존 hub-dashboard 정렬 불일치가 미해결이다. 3D 패널 추가로 정렬을 건드리지 않는다 |

## 6. 통합 전 반드시 해결해야 할 것 (현재 범위 밖)

### 🔴 인증이 전혀 없다
서버가 LAN에 열려 있고 세션 목록이 누구에게나 보인다.
**환자가 찍힌 3D는 민감정보다.** hub 연동 전 최소한 공유 토큰이 필요하다.

### 🟡 보관 정책이 없다
세션당 126MB가 무한 누적된다. 실측: 하루 11세션 = 1.2GB, 맥 여유 5.5GB.

### 🟡 3D는 통화·매칭보다 느리다
voice가 28초인데 3D는 촬영 30~60초 + 업로드 수십 초 + 융합이다.
**hub가 3D를 기다리면 안 된다.** "3D 없어도 정상 동작"이 시간축에서도 지켜져야 한다.

## 부록 — 현재 LiDAR_3D 상태 (2026-09-18 기준)

캡처 품질 검증 과정에서 확정된 사실들. 통합 설계 시 전제로 삼을 것.

| 사실 | 값 | 함의 |
|---|---|---|
| LiDAR 유효 측정 반경 | **약 2.5m** (사양 5m 아님) | 대원이 지나간 경로 반경 2.5m만 3D가 된다 |
| 메시 커버리지 | 최선 세션에서도 **18.7%** | "빈 공간 = 없음"이 아니라 "안 봄"이다 |
| ARKit 메시 격자 | **3cm 고정** (기기 무관) | 영역별 해상도 조절 API 없음 |
| iOS 버전에 따른 뎁스 신뢰도 | 26.6.1 **0.00%** vs 26.2.1 **73.56%** | 플랫폼 메시에 의존하면 결과를 통제할 수 없다 |
| 직접 융합 시 커버리지 | 25.1 → **257.1 m²** (10.2배) | 신뢰도 0% 기기도 되살릴 수 있다 |
| 적응형 해상도 (배경 4cm + 사람 1cm) | 전체 1cm 대비 **정점 19배↓, 시간 8.3배↓** | 부상자만 정밀 재구성이 가능하다 |
