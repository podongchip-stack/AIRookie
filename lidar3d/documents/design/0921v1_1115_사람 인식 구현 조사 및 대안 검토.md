## B. 핵심 검증 — 박스가 아니라 마스크다

### B-1. 마스크 면적 ÷ 경계상자 면적 (229프레임 전수)

```
중앙값 0.562   평균 0.576   최소 0.182   최대 0.844
0.95 이상(사각형에 가까움): 0프레임 (0.0%)
```

**1.0이면 박스다. 0.56은 명확한 윤곽이다.** 실루엣도 사람 형태로 나온다.

### B-2. 배경 누수 없음 — 두 볼륨이 상보적

```python
db = d.copy(); db[last] = 0     # 배경(4cm): 사람 픽셀 제외
do = d.copy(); do[~last] = 0    # 객체(1cm): 사람 픽셀만
```

추가로 **덩어리별 깊이 게이트**가 있다. 팔다리 사이로 보이는 뒷벽을 걸러내는데,
마스크 전체에 중앙값을 한 번 적용하면 사람이 여럿일 때 중앙값이 **사람들 사이 허공**에
잡혀 양쪽이 다 잘린다는 실패 기록과 함께 `connectedComponents`로 덩어리별 처리한다.

### B-3. 결과물 비교

| 파일 | 정점 | 표면적 | 크기(m) | 수직면 |
|---|---|---|---|---|
| `fused_adaptive.ply` | 373,545 | 132.0㎡ | 6.93×3.10×9.75 | 26.5% |
| `fused_objects.ply` | 259,742 | 15.2㎡ | 3.93×1.48×5.53 | **23.1%** |
| `scene_mesh.ply` | 146,890 | 81.3㎡ | 5.92×2.92×9.64 | 38.0% |

> **문서화된 과거 실패**: bbox 마스크를 썼을 때 "사람만" 메시가
> **4.6×1.3×2.4m 띠 모양, 수직면 49.4%**로 나왔다.
> 현재는 **23.1%**로 절반 이하다.

`fused_objects.ply`의 크기가 3.93×5.53m로 큰 것은 **사람 4명이 방 곳곳에 흩어져 있기
때문**이며, 사람별로 분리하면 0.83×0.96×0.82m 등 사람 크기가 나온다.

### B-4. 두 YOLO 경로는 별개다

| | `stage1_masks.py` | `detect_stage1/2.py` |
|---|---|---|
| 모델 | `yolov8l-seg` | `yolov8n` |
| 출력 | **마스크** | 박스 |
| 용도 | **적응형 해상도 + 사람 분리** | 뷰어 "검출된 물체" 마커 |
| 적응형 관여 | ✅ | ❌ (`objects_3d` 참조 0건) |

**뷰어에 보이는 YOLO 박스 패널은 적응형 해상도와 무관하다.**
"박스로 해상도를 올리는" 상황은 발생하지 않는다.

## C. ARKit 네이티브 분할 검토

### C-1. 현재 설정

`ARCaptureManager.configureAndRun()`:
```swift
config.sceneReconstruction = .meshWithClassification   // 폴백: .mesh → []
config.frameSemantics.insert(.sceneDepth)
// .smoothedSceneDepth 는 enableSmoothedSceneDepth = false 로 꺼져 있음
```

`personSegmentation` / `personSegmentationWithDepth` / `bodyDetection` — **흔적 0건**.

### C-2. 켤 수 있는가 — 가능하나 강력한 반대 근거가 있다

`.smoothedSceneDepth` **하나를 추가**했을 때의 실측이 코드 주석에 남아 있다:

> 15 Pro의 메시 생성이 **8,252 → 134 정점/이동m (-98%)로 붕괴**. 12 Pro는 -8%로 견딤.

`.meshWithClassification` + `.sceneDepth`만으로도 15 Pro가 **이미 한계**라는 뜻이다.
`personSegmentationWithDepth`는 매 프레임 신경망을 돌리므로 부담이 더 클 가능성이 높다.

### C-3. 해상도는 충분하다

`segmentationBuffer`는 256×192로 알려져 있는데, 공교롭게도 **우리 뎁스맵과 같은 해상도**다.
현재 YOLO 마스크도 이 해상도로 리샘플해 쓰므로 **`ARMatteGenerator`는 불필요**하다.

### C-4. 기기 지원 체크 — 패턴 존재

`supportsFrameSemantics` 체크가 `.sceneDepth` / `.smoothedSceneDepth`에 이미 있다.
같은 방식으로 추가 가능하다.

### C-5. 결정적 약점 — 설계 원칙과 충돌

ARKit 분할은 **실시간 프레임에서만** 나온다. 현재 구조는
**"앱은 원자료만 기록, 재구성은 맥에서"** 인데, ARKit 분할을 쓰려면
촬영 시점에 마스크를 저장해야 한다. 그러면:

- **재현 불가** — 나중에 파라미터를 바꿔 다시 돌릴 수 없다
- **Android 이식 시 경로가 갈라진다** — ARCore에 대응 API가 없다
- **앱이 무거워진다** — 이미 한계인 기기에 부담 추가

## D. 라이선스 — 가장 시급한 문제

### D-1. 확인 결과

```
Name: ultralytics   Version: 8.3.1   License: AGPL-3.0
Classifier: GNU Affero General Public License v3 or later (AGPLv3+)
가중치 체크포인트: license = "AGPL-3.0 License (https://ultralytics.com/license)"
```

**패키지와 가중치 양쪽 모두 AGPL-3.0이다.**

### D-2. 왜 문제인가

AGPL-3.0은 **네트워크를 통한 사용에도 소스 공개 의무**가 발생한다.
우리는 서버가 YOLO를 돌리고 그 결과를 웹 뷰어로 제공하므로,
이용자에게 **전체 소스를 제공할 의무**가 생길 수 있다.

골든링크가 **정부 조달이나 상용**으로 가면 실제 문제가 된다.

### D-3. 선택지

| 방안 | 비용 |
|---|---|
| 소스 공개 | 경쟁력·보안 측면 검토 필요 |
| Ultralytics 상용 라이선스 구매 | 비용 발생 |
| **permissive 모델로 교체** | 작업량 작음 (아래) |

### D-4. 교체 작업량 — 작다

구조가 잘 격리되어 있다:

- **`stage1_masks.py` 한 파일**만 고치면 된다 (`model.predict` → 다른 추론 호출)
- 출력 계약이 `person_masks.npz`(불리언 마스크)로 단순해서,
  **같은 형식으로 마스크만 내놓으면 하류 전부 그대로**다
  (`stage2_fuse.py`, `export_detection_overlay.py`가 소비처 전부)

후보별 유의사항:

| 모델 | 라이선스 | 유의점 |
|---|---|---|
| RF-DETR | Apache 2.0 | 분할 지원 여부 **실제 확인 필요** |
| D-FINE-seg | Apache 2.0 | 〃 |
| RTMDet | MIT | MMDetection 의존성이 무겁다 |

> ⚠️ 제안받은 "2026년 COCO·RF100-VL 벤치마크 1위" 같은 순위는 **이번 조사에서
> 검증하지 않았다.** 라이선스는 알려진 대로이나 성능 주장은 확인 없이 인용하지 않는다.

## E. 결론

### **(1) 현행 유지** — 권장

기술적으로 현재 방식이 용도에 맞다.

- 출력이 이미 **마스크**라 우려했던 문제가 없다 (실측 0/229 프레임이 사각형)
- 설정이 **추측이 아니라 실측**으로 정해져 있다
  (`l-seg` / `conf 0.15`, `imgsz` 640 유지 — 1280은 오히려 나빠짐)
- 적응형 해상도가 의도대로 동작한다 (수직면 49.4% → 23.1%)

### (2) ARKit 네이티브 전환 — **비권장**

15 Pro가 이미 한계라는 실측이 있고,
**"앱은 재구성하지 않는다"는 설계 원칙과 Android 이식 계획**을 정면으로 거스른다.

### (3) 외부 모델 교체 — **라이선스 사유로만**

성능 불만이 아니라 **AGPL-3.0** 때문이다. 구조가 잘 격리돼 있어 시기는 급하지 않지만,
**상용화·조달 논의가 시작되기 전에 해결**해야 한다.
