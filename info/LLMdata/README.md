# LLMdata — 필드 추출 LLM 학습 데이터

`goldenlink_extract`가 부르는 **필드 추출 LLM**(현재 `qwen3:14b`, 파인튜닝 대상은
`qwen3:8b`)의 학습 데이터를 모으는 곳이다. 종류별로 예시가 1건씩 들어 있다.

**OCR 모델은 학습 대상이 아니다.** DocLayout-YOLO와 PaddleOCR-VL은 그대로 두고,
그 결과 텍스트를 읽어 JSON을 만드는 부분만 학습한다.

```
서류 이미지 ─[OCR: 손대지 않음]→ 텍스트 ─[여기가 학습 대상]→ 그룹별 JSON
                                          qwen3:8b + LoRA
```

## 학습 단위는 "문서"가 아니라 "그룹 1회 호출"이다

`extractor.py`는 문서 1장당 LLM을 **4번** 부른다
(`document` / `night_duty` / `specialties` / `capabilities`). 그래서 학습 샘플도
호출 1회 단위다.

| 역할 | 내용 |
|---|---|
| `system` | `prompts.SYSTEM_PROMPT` 그대로 |
| `user` | `prompts.build_user_prompt(group, ocr_text)` 결과 — 그룹 지시문 + 원문 |
| `assistant` | 그 그룹의 JSON 응답 (`group.schema`를 만족하는 형태) |

`DocumentFields`(`ocr/output/*.json`)는 4개 응답을 파이썬이 합친 결과물이라
**학습 타깃이 아니다.** 여기에 그걸 넣으면 모델이 한 번도 만들지 않는 형식을
배우게 된다.

## 파일

| 파일 | 종류 | 줄 | 쓰임 |
|---|---|---|---|

| `raw/` | 수집 | — | 서류를 처리할 때마다 **자동으로 쌓이는** OCR 텍스트 = 학습 **입력** |
| `llm_raw/` | 수집 | — | 같이 쌓이는 LLM 가공 전 응답 = 학습 **타깃** |

| `01_labeling_sheet.jsonl` | **사람이 채움** | 10 | 값 단위 ○/× 판정. 나머지 파일의 원재료 |
| `02_sft.jsonl` | SFT | 4 | 조립된 정답. 그룹 4종 각 1건 (당직표) |

| `04_dpo_hallucination.jsonl` | DPO | 1 | 지어냄 |
| `05_dpo_missed.jsonl` | DPO | 1 | 놓침 |
| `06_dpo_evidence.jsonl` | DPO | 2 | 근거만 틀림 — **2026-08-04 실측에서 실제로 나온 실패** |
| `07_eval_gold.jsonl` | 평가 | 1 | 홀드아웃 정답지. **학습 금지** |

원문 3종은 서로 다른 역할을 맡는다.

| 문서 | 쓰임 |
|---|---|
| 당직표 | 값이 가장 많이 나오는 문서. 정답 예제의 기본 |
| 퇴원요약 | 당직·역량이 **없는** 문서. 미상 예제와 실측 실패 재현 |
| 진료의뢰서 | 평가 전용. 수신/발신 병원이 함께 적힌 함정 포함 |

## 왜 "미상 예제"를 따로 두는가 (`03`)

환각의 정체는 빈칸 메우기다. 값이 있는 예제만 학습시키면 모델은 "무언가는 내놓아야
한다"를 배우고, 빈칸을 그럴듯하게 채우는 습관이 오히려 강해진다.

미상 표현은 스키마가 이미 정해 두었다. 넷을 절대 섞지 않는다.

| 표현 | 뜻 | 나오는 곳 |
|---|---|---|
| `""` | 서류에 없다 | 기관명·기관코드·기준일자 |
| `-1` | 인원이 안 적혀 있다 (`0`명과 다르다) | `doctorCount` |
| `"UNKNOWN"` | 언급이 아예 없다 | `nightDuty`, `onDuty` |
| `[]` | 읽었는데 해당 없다 | `specialties`, `capabilities`, `equipment` |

전체 학습 데이터에서 **미상이 정답인 샘플이 30~40%는 되어야 한다.**

## 라벨 4종 (`01`의 `human.reasonCode`)

× 판정을 한 덩어리로 두면 학습 신호가 서로 상쇄된다. 지어냄을 밀어내면 모델이
보수적으로 가고, 놓침을 밀어내면 적극적으로 가야 하기 때문이다. 반드시 나눈다.

| 코드 | 뜻 | 학습 방향 | 검사기가 잡나 |
|---|---|---|---|
| `HALLUCINATED` | 원문에 없는 값 | 억제 | 대체로 잡는다 |
| `MISSED` | 원문에 있는데 안 뽑았다 | 촉진 | **못 잡는다** |
| `BAD_EVIDENCE` | 값은 맞는데 근거가 틀렸다 | 근거 인용 규율 | 잡는다 (값까지 같이 버린다) |
| `WRONG_PICK` | 검사는 통과했는데 판단이 틀렸다 | 판단 교정 | **못 잡는다** |

`MISSED`와 `WRONG_PICK`이 사람이 꼭 필요한 자리다. 나머지는 `grounding.py`가
자동으로 걸러 주므로, 사람은 **검사기를 통과했는데도 틀린 것**과 **아예 안 나온
것**만 보면 된다. 라벨링 대상이 1/3 이하로 줄어든다.

## 작업 순서

```
0. 원문 수집    서류를 시뮬레이션이나 run_extract.py --image 로 돌리면
                 raw/ 에 OCR 텍스트가 저절로 쌓인다 (아래 참고)
1. 후보 생성    같은 문서·그룹을 temperature 올려 8~16회 생성
                 (평소엔 temperature=0, seed=0 고정이라 1가지 답만 나온다)
2. 자동 판정    grounding.py 로 값 단위 채점 → 01 시트의 auto 칸
3. 사람 판정    검사기가 못 가르는 것만 ○/× + reasonCode → human 칸
4. 정답 조립    ○ 붙은 값을 모아 그룹별 정답 JSON → 02 / 03
5. SFT          02 + 03 으로 먼저 학습
6. DPO          × 값들을 04~06 형태 선호쌍으로 만들어 추가 학습
```

**4번이 핵심이다.** "여러 후보 중 완전한 정답 하나를 고른다"가 아니라 **조각을 모아
정답을 만든다.** 후보가 전부 불완전해도 문서를 버리지 않게 된다.

5번과 6번의 순서를 바꾸지 않는다. SFT로 형태를 먼저 잡고 DPO로 미세 조정하는 편이,
처음부터 선호쌍만 주는 것보다 안정적이다.

### `raw/` — 원문은 저절로 쌓인다

서류를 처리하면 OCR 텍스트가 `raw/`에 `YYYYMMDD_HHMMSS_<문서명>.json`으로 남는다.
따로 할 일이 없다.

| 실행 | `raw/` (입력) | `llm_raw/` (타깃) |
|---|---|---|
| `python simulation/gui.py` 에 서류 끌어놓기 | 쌓인다 (PDF도) | 쌓인다 |
| `run_extract.py --image <이미지>` | 쌓인다 | 쌓인다 |
| `run_extract.py --ocr-json <파일>` | 안 쌓인다 | 쌓인다 |

`--ocr-json`은 텍스트가 이미 파일에서 온 것이라 다시 쓰지 않는다(복사본만 는다).
추출은 새로 도므로 타깃은 쌓인다 — **프롬프트만 바꿔 다시 돌릴 때 이 조합을 쓴다.**
OCR을 건너뛰어 훨씬 빠르고, 입력이 글자 하나까지 같아서 프롬프트 효과만 분리된다.

**세 폴더가 같은 이름으로 남는다.** 시각을 한 번만 찍어 전부에 쓰기 때문이다.

```
LLMdata/raw/20260804_213000_당직표.json      OCR 텍스트        학습 입력
LLMdata/llm_raw/20260804_213000_당직표.json  LLM 가공 전 응답   학습 타깃
ocr/output/20260804_213000_당직표.json       추출 결과          판정 결과
```

`llm_raw/`의 파일 1개가 문서 1건이고, 그 안에 그룹 4개의 응답이 들어 있다.
`ocr/output/`은 근거 대조를 **거친 뒤**의 결과라 버려진 값이 빠져 있고,
`llm_raw/`는 **거르기 전**이라 모델이 실제로 뭐라고 답했는지가 그대로 있다.
그래서 학습 타깃은 이쪽이다.

```json
{
  "documentId": "당직표",
  "modelUsed": {"llm": "qwen3:14b"},
  "promptFingerprint": "59a9a96d62c4",
  "ocrText": "...",
  "groups": [
    {"key": "document",     "label": "서류 기본정보", "raw": {"hospitalName": "...", ...}},
    {"key": "capabilities", "label": "시술·장비",    "error": "JSON으로 못 읽었다: ..."}
  ]
}
```

실패한 그룹도 `error`로 남는다. 무엇이 왜 실패했는지가 프롬프트를 고칠 근거이고,
성공한 것만 모으면 실패가 통계에서 사라진다.

입력(`ocrText`)을 여기 한 번 더 담는 이유는 학습 레코드가 **한 파일 안에서**
짝이 맞아야 해서다. 폴더가 어긋나도 틀린 쌍이 만들어지지 않는다.

### `promptFingerprint` — 프롬프트가 바뀌면 갈라야 한다

지시문 전체(SYSTEM_PROMPT + 그룹 4개 instruction)의 해시다. 프롬프트를 고치면
그 전에 모은 응답은 **다른 질문에 대한 답**이 된다. 섞어서 학습시키면 어느 지시를
배운 건지 알 수 없어지므로, 학습셋을 만들 때 이 값으로 먼저 갈라낸다.

여기 쌓인 파일은 그대로 다시 넣을 수 있다. OCR은 장당 수십 초지만 텍스트만 있으면
추출은 GPU 없이 몇 초에 끝나므로, 프롬프트를 고쳐가며 비교할 때 쓴다.

```bat
python ocr\scripts\run_extract.py --ocr-json LLMdata\raw\20260804_213000_당직표.json
```

### 선호쌍은 한 축만 달라야 한다

채택본과 기각본이 여러 면에서 다르면 모델은 어느 차이를 배워야 할지 모른다.
기각본이 우연히 다 길었다면 "짧으면 좋다"를 배운다. `04`~`06`의 쌍은 전부
**한 항목만** 다르게 만들어 두었다.

## 목표 수량

| 항목 | 양 |
|---|---|
| 문서 | 150~300장 |
| 학습 샘플 | 600~1,200 (문서 × 4그룹) |
| 그중 미상 정답 | 30~40% |
| 평가셋 | 실물 서류 30~50장, **증강본 금지** |

LoRA로 출력 규율을 가르치는 작업이라 이 정도면 대체로 충분하다. 부족한 문서 수는
합성 서류와 OCR 텍스트 교란(띄어쓰기 흔들기, 일부 글자 손실)으로 메우되,
**평가셋만은 실물에서 떼어낸다.** 증강본으로 잰 숫자는 실전을 대변하지 못한다.

## 주의

### 파인튜닝해도 근거 대조는 걷어내지 않는다

파인튜닝은 모델 안에 판정기를 심는 게 아니라 확률을 기울인다. 학습 후에도 모델은
자기 출력을 검사하지 않으며, 환각 빈도가 줄 뿐 0이 되지 않는다.
`grounding.py`는 그대로 남는다 — 오히려 기각률이 파인튜닝 효과의 측정 지표가 된다.

### 구조화 출력(`format`)도 계속 쓴다

형식은 JSON Schema 제약 디코딩이 보장한다. 파인튜닝으로 형식을 배웠으니 제약을
빼자는 건 손해다. 파인튜닝은 **무엇을 넣고 뺄지의 판단**에만 쓴다.

### 프롬프트가 바뀌면 이 파일들도 다시 만들어야 한다

`user` 내용은 `prompts.py`에서 생성한 것이다. 지시문이나 어휘(`vocabulary.py`)를
고치면 학습 데이터의 프롬프트가 실전과 어긋난다. 손으로 고치지 말고
`prompts.build_user_prompt()`로 다시 생성한다.

### 베이스라인을 먼저 잰다

지금 실측은 `qwen3:14b` 3건뿐이다. **`qwen3:8b` 제로샷 숫자를 먼저 재 둬야**
나중에 나온 결과가 파인튜닝 효과인지 14b→8b 손실을 겨우 메운 것인지 구분된다.
모델은 `GOLDENLINK_LLM_MODEL` 환경변수로 바꾼다 (코드 변경 없음).

### 개인정보

지금 들어 있는 3종은 전부 가상 문서이고 이름은 `홍○○` 형태로 비식별화돼 있다.
실물 서류를 넣을 때는 환자 이름·등록번호·생년월일을 지운 뒤 넣는다
(CLAUDE.md 개인정보 최소 수집 원칙). 실물이 들어오는 시점에 이 폴더를
`.gitignore`에 추가할지 정해야 한다 — 지금 예시는 가상이라 커밋해도 된다.

## 학습 환경

Ollama는 학습을 못 한다. 학습은 conda `ml` 환경에서 하고, 끝나면 되돌린다.

```
merge → GGUF 변환 → Modelfile 등록 → ollama create
```

RTX 5080 16GB에서 14B는 QLoRA로도 빠듯하다(서류 원문이 들어가 시퀀스가 길다).
8B가 현실적이고, 코드는 환경변수만 바꾸면 되므로 수정할 것이 없다.
