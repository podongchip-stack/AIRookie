## 0. 프레이밍 — "제안한 방식"이 정확히 무엇인가

제안서의 핵심은 **AI를 양 끝단으로 밀어내고 가운데 판정은 순수 규칙**으로 두는 것이다.

```
voice : LLM 자유 텍스트 ──[LLM 분류 / enum 제약]──→ 표준 코드   (필요역량)
info  : 병원 제각각 표기 ──[정규화]───────────────→ 표준 코드   (보유역량)
hub   : 코드 ↔ 코드 정확 대조 (임계값 없음, 결정적)
```

판정은 두 층으로 나뉜다.

| 층 | 방식 | 대상 |
|---|---|---|
| 하드필터 (없으면 탈락) | 코드 정확 대조 | 시술 가능 여부, 병상 종류, 응급실 운영 여부 |
| 소프트 점수 (순위) | 가중합 | 거리, 병상 수, 근거 강도 점수 |

### 왜 임베딩을 판정 자리에서 빼는가 (제안서 §2)

1. **시연 시나리오 3개 중 2개가 기존 스키마로는 성립하지 않는다.** 뇌졸중 → 재관류
   가능 병원을 고르려면 시술 정보를 담을 필드가 필요한데 "신경과 있음"까지만 표현
   가능했고, 소아 환자 분기는 `availableBedCount` 숫자 하나뿐이라 **성인0/소아2인
   병원과 성인2/소아0인 병원이 똑같이 "2"로 보였다.**
2. **임베딩은 능력의 유사도가 아니라 이름의 유사도를 잰다.** `신경과`↔`신경외과`는
   글자가 거의 같지만 tPA를 놓는 과와 개두술을 하는 과이고, `심혈관센터`↔`순환기내과`↔
   `CV Lab`은 글자가 다른데 능력이 같다. **붙여야 할 걸 떼고, 떼야 할 걸 붙이는**
   방향의 오류다.
3. **임계값을 정할 근거 데이터가 없다.** 유사도 컷을 0.6에 둘지 0.7에 둘지 정할
   실데이터가 없다. 학습 데이터가 없어 ML을 배제했던 것과 같은 문제가 임계값 튜닝에서
   되살아난다. **코드 대조에는 임계값이 없다.**
4. **팀 원칙과 더 잘 맞는다.** 구급대원에게 제시할 근거가 "혈전제거술 가능 → 통과"인
   편이 "유사도 0.82점"보다 낫다.

### 15그룹이 이 구조를 그대로 잇는다

경로 C가 내보내는 **15그룹 역량 벡터**(`assessment.groups`)는 그 자체가 **닫힌 enum
15개**다. voice가 예상 병명을 15그룹 중 하나로 고르면(structured output / enum 제약)
hub는 `groups[그룹명]`을 **딕셔너리로 조회**하면 끝이다 — 유사도도 임계값도 없다.

그룹 이름이 `재관류중재술`·`뇌출혈수술`·`중증화상`처럼 **능력 단위**로 이미 갈라져
있어서, `신경과`↔`신경외과` 같은 이름 유사도 문제가 구조적으로 들어오지 않는다.

> 임베딩을 **그룹을 고르는 보조**로 쓰는 것은 여전히 가능하다. 다만 그건 판정이 아니고,
> 고른 뒤의 대조는 어느 쪽이든 정확 조회다.

## 2. 점수 산출 방식 (`hospital_score/scoring.py`)

### 2-1. 산출물 형태 — 병원당 단일 점수를 만들지 않는다

심근경색 환자와 화상 환자에게 같은 병원의 수용가능성이 다르므로 축을 둘로 나눈다.

| 축 | 성격 | 재료 |
|---|---|---|
| 여건 (`conditions`) | 환자 무관 · **스칼라** | 병상 가동률, 과밀, 피드 신선도 |
| 역량 (`groups`) | 환자 의존 · **15그룹 벡터** | 중증질환 수용가능 신고 28항목 |

### 2-2. 왜 "최적값"을 찾지 않나

최적화하려면 정답이 있어야 하는데 **"이 병원이 이 환자를 실제로 받았는가"의 정답이
없다.** 쓸 수 있는 대용 정답도 전부 부족하다 — 병원의 `불가능` 신고는 전체의 1.2%인
데다 그건 우리 **입력**이지 정답이 아니고, 전문병원 지정은 5개 분야뿐이다. 여기서
억지로 최적화하면 **없는 정답을 지어내는 것**이 된다.

그래서 셋으로 대신한다.

1. **불변식** — 점수가 반드시 지켜야 할 순서를 코드로 못박고 검사한다
   (`INVARIANTS`, `--check`). 라벨 없이 검증되고, 가중치를 어떻게 잡든 이게 안 깨지면
   된다. **실제로 대부분의 파라미터 논쟁이 여기서 사라졌다.**
2. **실패 비용의 비대칭** — 받을 수 있는 병원을 후보에서 빼는 것(골든타임 손실)이 못
   받는 병원을 올리는 것(전화 한 번 더)보다 훨씬 비싸다. **애매하면 남긴다.**
3. **계층** — 근거 강도의 순서만 정한다. 근거 없이 `0.73` 같은 값을 두면 임의값에
   정밀함의 외양만 입히는 것이다.

### 2-3. 계층 5단계 — 점수의 전부

```
불가능 신고 0.2  <  근거 없는 미상 0.4  <  전문의 있는 미상 0.6
                 <  전문병원 지정 미상 0.8  <  가능 신고 1.0
```

| 계층 | 조건 | score | confidence |
|---|---|---|---|
| `declared_yes` | 병원이 가능하다고 신고 | 1.0 | high (stale이면 medium) |
| `unknown_designated` | 미상 + 그 분야 전문병원 지정 | 0.8 | medium |
| `unknown_specialist` | 미상 + 해당 진료과 전문의 보유 | 0.6 | low |
| `unknown_bare` | 미상 + 근거 없음 | 0.4 | low |
| `declared_no` | 병원이 불가능하다고 신고 | 0.2 | high |

`score = tier / 5`. **점수는 오직 계층에서만 나온다** — 다른 요인이 섞이면 순서가
깨지고, 불변식 검사가 그걸 잡는다.

### 2-4. 항목 하나의 판정 순서

```
신고가 'Y'        → declared_yes (5)
신고가 '불가능'    → declared_no  (1)
'정보미제공'       → ① 그 분야 전문병원으로 지정됐나  → unknown_designated (4)
                   ② 해당 진료과 전문의가 있나       → unknown_specialist (3)
                   ③ 둘 다 아니면                    → unknown_bare       (2)
```

**전문의를 한 칸만 올린 것은 의도적이다.** 심평원 진료과가 대분류(`순환기내과` 없이
`내과`)까지만 와서 특정성이 낮고, 실제로 `불가능`이라 신고한 칸의 **91.2%도 해당 과
전문의를 보유**하고 있었다. 그래서 전문의는 점수를 **올리는** 근거가 아니라 "역량
없음으로 단정하지 못하게 막는" **하한**으로만 쓴다.

### 2-5. 그룹 점수 = 그룹 내 **최댓값**

한 그룹에 항목이 여럿일 때(예: `[산부인과응급]` = 분만·산과수술·부인과수술) 가장 높은
근거를 택한다. 실패 비용이 비대칭이라 보수적으로 낮추지 않는다.

### 2-6. `score`와 `confidence`는 끝까지 곱하지 않는다

섞으면 **"확실히 낮음"과 "모르겠음"이 구분되지 않는다.** 미상과 확인된 만실을
구분해온 기존 원칙과 같은 논리이며, 불변식 검사 항목이기도 하다.

### 2-7. 검증 — 정답이 없으므로 둘로 대신한다

**① 불변식 검사** (`python -m hospital_score.scoring --check`)

```
계층 순서 4개                     불가능 < 근거없는미상 < 전문의미상 < 지정미상 < 가능
미상이 '불가능' 이하로 평가되지 않는다
score가 tier와 어긋나지 않는다     (점수는 계층에서만 나온다)
근거(basis)가 비어 있는 항목이 없다
신뢰도 값이 어휘 밖으로 새지 않는다
```

**② 전문병원 지정 홀드아웃** (`--validate`) — 표본이 작지만(분야당 1~6곳) 방향은
확실히 검증된다.

| 분야 | 지정·매칭 | 신고만 볼 때 | 새 점수 |
|---|---|---|---|
| **화상** | 4 | **0** | **4** |
| 수지접합 | 5 | 2 | 5 |
| 뇌혈관 | 4 | 3 | 4 |
| 산부인과 | 2 | 0 | 2 |
| 심장 | 1 | 1 | 1 |

**화상 전문병원은 기존 파이프라인에서 한 곳도 후보에 오르지 못한다.** 전부
"정보미제공"이라 존재하지 않는 것처럼 취급되기 때문이다.

### 2-8. 폐기·보류 판정 (되살리지 말 것)

| 안 | 죽은 이유 |
|---|---|
| 병상 수 예측 | `P(만실 전환) = 0.568%` (95% CI 0.41~0.78%, 서울 6,519쌍·10분 지평 / 전국 0.301%) — **사전 등록한 폐기 기준 2%** 미달 |
| 미상 추정 모델 | 관측 3,574칸 중 **95.6%가 "가능"**(서울 97.3%) → 상수 기준선이 이미 95점. 라벨이 상위 등급 편중(MNAR — 명부 21.8%인 최하위 등급이 라벨의 0.7%만 내놓음)이라 미신고 병원에 적용하면 "미신고 병원도 대부분 수용 가능"이라는 **위험한 방향**의 오류 |
| 병상 미상 보간 | 미상이 서울 55곳 중 0~1곳 — 문제 크기가 사실상 0 |
| 도착 시점 병상 예측 | `hvidate` 갱신 경과 중앙값 5분, 443곳 중 88.7%가 10분 이내 — 메울 공백이 없음 |
| 중증도별 재실시간(LOS) 추정 | 정답(실제 체류시간)을 관측할 방법이 없음 |
| OCR 병원 특화도 프로파일 | 심평원이 이미 제공 + 실제 병원 서류를 구할 수 없음 |

> **추정 대신 계층을 택했다.** 미상 칸을 모델로 채우지 않고 **외부 근거의 유무로
> 순위만** 나눈다. 전문의 보유·전문병원 지정은 관측된 사실이라 "모델이 지어낸 값"이
> 아니고, 미상은 끝까지 `status: "unknown"`으로 남는다.

| 6 | (제안) info → hub | `POST /info/hospitals` | `HospitalInfo` + **`assessment`** | 30분 | **동시 배포 대기** |

- 포트: **hub 5001 / info 5002(고정) / 거절 로그 단독 실행 시 5003**
- URL은 전부 환경변수로 교체 가능 — `HUB_HOSPITALS_URL`, `HUB_AMBULANCES_URL`,
  hub 쪽 `INFO_BED_UPDATE_URL`

### 3-2. 입력 근거 소스 (외부 API)

| 소스 | 경로 | 얻는 것 |
|---|---|---|
| E-Gen 목록정보 | `getEgytListInfoInqire` | 좌표, **응급의료기관 등급(`dutyEmclsName`)** |
| E-Gen 가용병상 | `getEmrrmRltmUsefulSckbdInfoInqire` | 병상 6종, 총병상(`hvs38`), 입력시각(`hvidate`), 장비(CT/ANGIO) |
| E-Gen 중증질환 | `getSrsillDissAceptncPosblInfoInqire` | `MKioskTy1`~`MKioskTy28` (`Y`/`불가능`/`정보미제공` 3종) |
| 심평원 병원정보 | 15001698 `hospInfoServicev2/getHospBasisList` | `ykiho`·좌표·총 의사 수 — **조인의 출발점** |
| 심평원 의료기관별상세 | 15001699 **`MadmDtlInfoService2.8`** (11종) | **전문과목별 전문의 수** |
| 심평원 전문병원 지정 | 15051054 `api.odcloud.kr` | 분야별 **114곳** |

- **서비스키는 E-Gen과 같은 값이다.** data.go.kr은 계정당 인증키가 하나이고 서비스별
  활용신청만 따로 필요하다. `.env`에 `HIRA_SERVICE_KEY` 한 줄 추가.
- 심평원 일일 트래픽 800,000회 — 사실상 제약이 없다.

**⚠️ 엔드포인트 버전 함정 (실제로 몇 시간을 날린 지점)**

구버전 `MadmDtlInfoService2.7`도 게이트웨이에 **실재해서 403(권한 없음)을 돌려준다.**
이걸 보고 "경로는 맞고 승인만 안 났다"고 오진하기 쉽다.

```
400 NO_OPENAPI_SERVICE             = 그런 경로가 없다
403 SERVICE_KEY_IS_NOT_REGISTERED  = 경로는 실재하나 이 키에 권한이 없다
```

**403은 "그 경로가 실재한다"만 알려줄 뿐 "그게 현재 버전이다"라는 뜻이 아니다.**
버전은 반드시 포털 마이페이지 활용신청 상세 화면의 **End Point** 줄로 확인할 것.

### 3-3. E-Gen ↔ 심평원 조인 — 공통 식별자가 없다

`hpid` ↔ `ykiho`. 요양기관기호도 사업자번호도 없어서 **좌표 최근접**으로 붙인다
(`send_to_hub.py`의 Supabase 대응표가 같은 문제를 같은 방법으로 푼 선례).

| 거리 | 매칭 | 비율 |
|---|---|---|
| 100m 이내 | 490/533 | 91.9% |
| 300m 이내 | 512/533 | 96.1% |
| **1.2km 이내** | **518/533** | **97.2%** |

오차 중앙값 **11m**. 미매칭 15곳은 전부 보건의료원·보건지소로, 병원급만 조회한
탓이지 매칭 실패가 아니다.

**기관명 정규화만으로는 92.7%였다** (`의료법인대산의료재단익산병원` ↔ `익산병원`처럼
표기가 달라 놓치는 것들). 좌표가 없는 데이터(전문병원 지정 현황)는 이름으로 붙일
수밖에 없고, **그 결과는 하한으로 읽어야 한다.**

## 4. 어떤 내용을 주는가 (페이로드 실물)

### 4-1. 현재 상시 전송 — `HospitalInfo`

```json
{
  "hospitalId": "S0000001",
  "name": "서울대학교병원",
  "gps": { "lat": 37.5796, "lng": 126.9995 },
  "availableBedCount": 12,
  "nightDutyAvailable": true,
  "specialties": [
    { "department": "순환기내과", "doctorCount": 0,
      "recentProcedureTags": ["응급 관상동맥중재술"] }
  ],
  "source": "rule",
  "updatedAt": "2026-08-13T01:15:02+09:00",
  "bedsByType": { "ER_ADULT": 12, "ICU": 3, "OR": 5 },
  "capabilities": ["EQP_CT_24H", "PROC_PCI_EMERGENCY"]
}
```

| 필드 | 타입 | 비고 |
|---|---|---|
| `hospitalId` | string | **현재는 Supabase 체계 `S0000001`~`S0000007`** (§5.1에서 변경) |
| `gps.lat` / `gps.lng` | number | hub의 거리 계산에 그대로 쓰임. `lon`이 아니라 `lng` |
| `availableBedCount` | int ≥ 0 | 미상이면 0. **미상 여부는 `bedsByType` 키 유무로 구분** |
| `nightDutyAvailable` | bool | 공개 API에 당직 정보가 없어 중증질환 수용가능을 프록시로 씀 |
| `specialties[]` | object[] | 역량 코드에서 역산해 만든 진료과 |
| `bedsByType` | dict (확장) | **미상인 종류는 키 자체를 넣지 않는다** |
| `capabilities` | string[] (확장) | 역량 코드 7종. **하드필터 대조 대상** |

**전송 방식**: 병원 1곳당 POST 1회. `to_hub_json()`이 `exclude_none=True`로 값 없는
선택 필드를 아예 빼고 보낸다.

### 4-2. 표준 코드 어휘 (`schema.py`가 원본)

**병상 6종** — E-Gen 필드에서 **전부 채워진다.**

| 코드 | E-Gen 필드 | 신고 병원 (서울 55곳 중) |
|---|---|---|
| `ER_ADULT` | `hvec` 일반 | 55 |
| `ER_PEDIATRIC` | `hv28` 소아 | 23 |
| `ER_NEGATIVE` | `hv29` 응급실 음압격리 | 37 |
| `ICU` | `hvicc` [중환자실] 일반 | 35 |
| `CCU` | `hv34` [중환자실] 심장내과 | 12 |
| `OR` | `hvoc` [기타] 수술실 | 54 |

**역량 7종** — 6종은 채워지고 **1종은 영영 못 채운다.**

| 코드 | 출처 | 보유 병원 (서울 55곳 중) |
|---|---|---|
| `EQP_CT_24H` | `hvctayn` (가용병상 응답) | 54 |
| `EQP_ANGIO_SUITE` | `hvangioayn` (가용병상 응답) | 38 |
| `PROC_PCI_EMERGENCY` | `MKioskTy1` | 33 |
| `PROC_CRANIOTOMY` | `MKioskTy3`·`MKioskTy4` | 31 |
| `PROC_EVT_THROMBECTOMY` | `MKioskTy2` | 29 |
| `PROC_CESAREAN_EMERGENCY` | `MKioskTy17` | 22 |
| `PROC_IV_THROMBOLYSIS` | **대응 항목 없음** | **0** |

> `PROC_IV_THROMBOLYSIS`(tPA)가 **OCR의 존재 이유**다. 뇌경색은 재관류중재술
> (`MKioskTy2`)로만 묻고 정맥 혈전용해술은 따로 묻지 않아, 공개 API로는 채울 수 없다.
> 제안서의 뇌졸중 시나리오와 직결되는 지점이다.

어휘 밖의 값은 **만드는 순간 실패한다**(`schema.py`의 validator). voice가 보내는
"필요역량"과 info가 올리는 "보유역량"이 같은 어휘여야 hub가 대조할 수 있는데, 한쪽이
임의 코드를 쓰면 **에러 없이 조용히** 매칭에서 빠지기 때문이다.

### 4-3. 결측 처리 규약 — `0`과 "미상"을 절대 섞지 않는다

| 원본 값 | 의미 | 표현 |
|---|---|---|
| `5` | 관측된 가용 병상 | `bedsByType`에 키가 있고 값이 `5` |
| `0` | **확인된 만실.** 갈 수 없다 | `bedsByType`에 키가 있고 값이 `0` |
| `-24` | **과밀.** 정원보다 24명 많다 | `0`으로 낮춰 담고, 원래 값은 리포트·스냅샷에 남긴다 |
| `-1` | 미입력. 알 수 없다 | `bedsByType`에 **키 자체가 없음** |
| 필드 누락 | 미입력 (E-Gen은 이렇게도 표현한다) | `bedsByType`에 **키 자체가 없음** |
| 총 병상 초과 | 입력 오류. 값이 아니다 | **키 없음** + 리포트 |

**`-1`만 미입력이다.** `-2` 이하는 과밀이며, 둘을 뭉개면 **가장 갈 수 없는 병원이
"모르는 병원"으로 남아** 후보에 계속 오른다.

### 4-4. 제안 전송 — `assessment` (기존 객체의 superset, 키 하나 추가)

```jsonc
{
  "hospitalId": "A1100038", "name": "…", "gps": {…},   // ← 기존 필드 전부 그대로
  "availableBedCount": 30, "bedsByType": {…}, "capabilities": […],

  "assessment": {
    "assessedAt": "2026-08-13T01:20:00+09:00",
    "source": "rule",
    "conditions": {                    // 환자와 무관한 여건
      "availableBeds": 30, "totalBeds": 146, "bedOccupancy": 0.795,
      "overcrowded": false, "bedCountUnknown": false,
      "feedAgeMinutes": 3539915,
      "stale": true,                   // 하루 넘게 갱신 없음
      "missingFromFeed": false         // 명부엔 있는데 응답에 없음 (병상 0과 다르다)
    },
    "evidence": {                      // 기계 판독용 대조값
      "designatedFields": ["화상"],
      "specialists": { "성형외과": 7, … },
      "hvidate": "20191119…",
      "equipment": { "CT": "Y", "ANGIO": "Y" }
    },
    "groups": {                        // 환자에 따라 달라지는 15그룹
      "중증화상": {
        "status": "unknown",           // available / unavailable / unknown
        "tier": "unknown_designated",
        "score": 0.8,
        "confidence": "medium",
        "basis": [                     // 구급대원에게 그대로 보여줄 근거
          "병원 신고 없음(정보미제공)",
          "전문병원 지정: 화상",
          "마지막 입력 2458일 전",
          "등급: 응급실운영신고기관"
        ],
        "items": { "19": "정보미제공" } // 그룹을 이룬 항목별 원본 신고값
      }
      // … 15그룹
    }
  }
}
```

- **크기**: 병원당 약 **5.1KB**, 533곳 전체 약 **2.2MB**
- 실물은 `python -m hospital_score.scoring --payload 한강성심`으로 찍어볼 수 있다
- **`basis`(사람이 읽는 문장)와 `evidence`(기계가 읽는 대조값)를 분리**했다. evidence에는
  **판정에 실제 쓰인 진료과만** 싣는다 — 원자료를 통째로 넘기면 심평원 도메인 지식
  (진료과 코드 체계·`ykiho`·전문병원 분야명)이 hub에 복제되고, 심평원 스키마가 바뀔 때
  hub까지 깨진다(2.7 → 2.8 같은 일)
- ⚠️ **이름 충돌 주의**: 기존 `capabilities`(역량 코드 7종 `list[str]`) ≠
  `assessment.groups`(15그룹 판정). 서로 다른 것이라 네임스페이스를 분리했다
- ⚠️ **hub의 pydantic이 unknown 필드를 거부하면 보내는 순간 기존 연동이 깨진다.**
  info 혼자 배포할 수 없고 hub와 동시에 가야 한다

**hub가 쓰는 방법 (권장)**

1. 예상 병명 → **15그룹 중 하나를 고른다** (enum 조회, 유사도·임계값 없음)
2. 그 그룹의 `score`(0.2~1.0)와 거리 점수를 **hub가 정한 비중으로** 합산
3. `confidence`는 **점수에 곱하지 말고** 화면에 그대로 표시
4. `status`가 `unavailable`이어도 **후보에서 제거하지 말고 아래로 내릴 것**
5. `basis`를 dashboard에 그대로 노출 — "왜 이 병원인가"의 답이다

> **절대값과 비중은 info가 정하지 않는다.** "2km 가깝지만 근거가 약한 병원 vs 5km
> 멀지만 확실한 병원"의 트레이드오프는 거리를 가진 hub가 결정할 문제다. info는
> **순서와 근거만** 준다.

### 4-5. 거절 로그 (info가 받는 쪽) — 어휘 4축

```jsonc
// 지금 hub가 dashboard에서 받는 거절 액션을 그대로 전달해도 기록된다
{"action": "hospital_reject", "hospital_id": "A1100026", "timestamp": "…"}

// 나중에 이유가 붙으면
{"caseId": "case-abc", "hospitalId": "A1100026", "diseaseGroup": "중증화상",
 "reasonCode": "ON_CALL_MISMATCH", "declaredAtRequest": "Y", "timestamp": "…"}
```

| 축 | 이유 코드 | 무엇을 갱신하나 |
|---|---|---|
| 구조적 | `NO_WARD` `NO_DEPARTMENT` `NO_EQUIPMENT` | 역량 벡터 수정 = **E-Gen 신고가 틀렸다는 증거** |
| 주기적 | `ON_CALL_MISMATCH` `NIGHT_UNAVAILABLE` | 시간대·요일 패턴. 상수 점수에 반영하면 안 됨 |
| 순간적 | `BEDS_FULL` `OR_OCCUPIED` `STAFF_BUSY` | 그때의 여건. 병원 속성이 아님 |
| 환자 요인 | `SEVERITY_EXCEEDED` `AGE_LIMIT` | 병원 속성이 아니라 환자-병원 조합 |
| 미분류 | `NO_RESPONSE` `UNSPECIFIED` `OTHER` | — |

- **필수 필드는 `hospitalId` 하나**(`hospital_id`/`hpid` 표기도 받는다). 이유가 없으면
  `UNSPECIFIED`로 기록 → **hub는 스키마를 안 바꿔도 오늘 당장 연동된다**
- **모르는 필드는 버리지 않고 `extra`에 보존**한다. 받는 쪽에서 까다롭게 굴면 저쪽이
  못 붙이고, 그 사이 로그는 **영영 사라진다**(소급 생성 불가)
- **왜 4축인가**: 화상 병동이 아예 없어서 거절한 것과 그날 당직이 정형외과라서 거절한
  것을 같게 다루면, **일시적 사정 때문에 그 병원을 영구히 후보에서 밀어내게 된다.**
  뺑뺑이를 줄이려다 선택지를 좁히는 결과다
- `declaredAtRequest`(물어볼 당시 신고값)를 같이 받으면 **"가능이라 신고했는데 거절"**을
  셀 수 있다 → **신고 정확도를 운영 데이터로 직접 측정**
- ⚠️ **`NO_RESPONSE`를 반드시 남길 것.** 거절 로그는 우리가 후보로 올린 병원에서만
  생기므로, 그것마저 없으면 **낮은 점수가 낮은 점수를 재생산하는 되먹임**이 생긴다

**현재 거절 로그는 점수에 반영되지 않는다.** `scoring.py`는 `rejection.py`를 아예 읽지
않는다(0건 상태로 검증 완료). 지금은 쌓기만 한다.

## 5. 후속 작업 (2026-08-13 hub와 합의)

### 5-1. 🔴 hub로 흐르는 병원을 7곳 → 533곳으로

```
E-Gen 실 API   533곳
   ↓  send_to_hub.py  _remap_to_supabase_hpid()   ← 대응표에 없으면 전부 버림
hub              7곳
```

**원인은 병상이다.** hub가 이송 확정 시 병상을 차감해야 하는데 E-Gen이 조회 전용이라
병상만 Supabase에서 읽고 있고, 그 Supabase에 7곳만 있어서 목록 전체가 7곳으로 묶였다.
그 7곳은 전부 서울이라 **지방 이송은 후보가 0곳**이다.

**합의된 해법**: 병상 차감을 Supabase가 아니라 **짧은 TTL(10~15분) 오버레이**로 관리하고
병상 자체는 E-Gen 실값을 쓴다 → Supabase 의존 제거 → 대응표 불필요 → 533곳 전부 hub로.

**근거**: `hvidate` 갱신 경과 **중앙값 5분**(443곳 중 88.7%가 10분 이내). E-Gen은 실제로
계속 갱신된다. 그렇다면 "info 재조회(30분) 때 우리 차감이 리셋된다"는 기존 설계 전제를
다시 봐야 한다 — 낡은 값으로 되돌아가는 게 아니라 **병원이 직접 갱신한 진짜 값으로
바뀌는 것**이라, 오히려 우리 차감이 그걸 덮고 있으면 더 부정확하다.

**딸려오는 변경**: `hospitalId`가 `S0000001~7` → 실 hpid(`A1100017` 등). 병원 대시보드가
`?id=`로 라우팅하므로 **dashboard 확인 필요.**

### 5-2. 🔴 거절 사유 수집 시작 — 늦어질수록 손해

- **hub**: `POST /hub/rejection`으로 중계만 하면 된다. 스키마 변경 불필요
- **dashboard**: "수용 불가" 버튼에 사유 선택 추가 (`rejection --vocab`)

### 5-3. 🟡 `assessment` 필드 수용 — hub와 동시 배포

`schema.py`는 `extra="forbid"`인 팀 합의 계약 파일이라 필드 추가에 합의가 필요하다.
info 후속 작업은 `fetch_hospitals()` 결과에 `score_hospital()` 결과를 얹는 배선.

### 5-4. 🟡 stale 표시

전국 **25곳**이 하루 넘게 방치된 병상 값을 실시간처럼 송출 중이고 최고 **8.6년**이다.
hub가 `availableBedCount`로 순위를 매기기 시작하면 즉시 문제가 된다.
`assessment.conditions.stale` / `feedAgeMinutes`로 이미 실어 보낼 수 있다.

### 5-5. 🟢 dashboard 표시 규약

- `bedCountUnknown: true`면 "0"이나 "병상 없음"이 아니라 **"미상"**으로
- `assessment.groups[*].basis`를 그대로 노출 — 구급대원의 판단 근거
- `confidence`를 점수와 **별도로** 표시

## 6. 보고서에 실을 실측 근거

전부 `python -m hospital_score.report`로 재현된다 (**API 호출 0회**, 쌓인 스냅샷만 읽음).

| 발견 | 숫자 |
|---|---|
| 하루 넘게 방치된 병상 값을 실시간 송출 | 전국 **25곳**, 최고 **8.6년**(3,144일) |
| 전국 가용병상 **1위**가 유령 값 | 한강성심병원 30병상 = **2,457일** 묵음. 2위부터는 전부 10분 이내 갱신 |
| 방치 병원의 등급 | **25곳 전부 응급실운영신고기관** (해당 등급 27곳 중 25곳 = 93%) |
| 중증질환 신고 미상률 | 전체 **70.8%**, 등급별 21.4% → 53.0% → 88.2% → **96.4%** 계단식 |
| 명부엔 있는데 응답에 없는 병원 | 응급실운영신고기관 116곳 중 병상 API에 **27곳만** (≠ 병상 0) |
| 화상 전문병원 | 5곳 중 E-Gen에 화상 역량이 보이는 곳 **0곳** |
| 소아 항목의 숨은 조건 메시지 | 정보미제공 1,935칸 중 206칸(10.6%)에 조건 메시지, 그중 22칸은 메시지가 아예 `불가능` |
| `hvidate` 갱신 경과 | 중앙값 **5분**, 443곳 중 **88.7%가 10분 이내** |
| E-Gen ↔ 심평원 조인 | **518/533 = 97.2%**, 오차 중앙값 **11m** |

**이 숫자들이 말하는 것**: `dutyEmclsName`(응급의료기관 등급) 하나가 신고 성실도를 거의
그대로 설명한다(미상률 21.4% → 96.4%). 그런데 **이 필드는 E-Gen 목록정보에 이미 오는데
지금 파이프라인 어디에서도 쓰이지 않는다.**
