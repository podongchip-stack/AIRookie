# 병원 정보 ↔ 매칭 인터페이스 변경 제안

- **작성**: 최준혁 (`feature/info`)
- **대상**: `feature/hub`, `feature/voice`
- **작성일**: 2026-07-31
- **상태**: 제안 — 실측 검증 후 확정 논의 예정

---

## 1. 한 줄 요약

지금은 **매칭 판정을 임베딩 유사도 점수로** 하고 있습니다. 이를 **표준 역량 코드의
정확 대조**로 바꾸고, 임베딩은 판정 자리에서 빼서 **`feature/info`의 데이터 정규화
단계로 이동**시키자는 제안입니다.

기존 코드를 걷어내자는 게 아니라 **한 겹 얹는 방식**이며, `feature/dashboard`는
변동이 없습니다.

---

## 2. 왜 바꾸려는가

### ① 시연 시나리오 3개 중 2개가 현재 스키마로는 성립하지 않습니다

| 시나리오 | 현재 가능? | 이유 |
|---|---|---|
| 뇌졸중 → 재관류 가능 병원 선택 | ✗ | 시술 정보를 담을 필드가 없음. "신경과 있음"까지만 표현 가능 |
| 소아 환자 → 소아 병상 필터 | ✗ | `availableBedCount` 숫자 하나뿐. 성인0/소아2 병원과 성인2/소아0 병원이 **동일하게 "2"** 로 보임 |
| 만실 → 2순위 대체 | ✓ | 문제없음 |

이 두 시나리오가 하필 "가장 가까운 병원 ≠ 정답"을 증명하는 핵심입니다. 빠지면
거리순 정렬과 구분이 어려워집니다.

### ② 임베딩이 가장 중요한 구간에서 틀릴 위험이 있습니다

임베딩은 *능력의 유사도*가 아니라 *이름의 유사도*를 잽니다. 한국 진료과명은 이 둘이
어긋납니다.

- `신경과` ↔ `신경외과` — 글자가 거의 같아 유사도는 높지만, **tPA를 놓는 과와
  개두술을 하는 과**입니다. 뇌졸중 시나리오에서 이 둘을 구분하지 못하면 시연이
  무너집니다.
- `심혈관센터` ↔ `순환기내과` ↔ `CV Lab` — 글자는 다른데 능력은 같습니다. 유사도는
  낮게 나올 가능성이 큽니다.

**붙여야 할 걸 떼고, 떼야 할 걸 붙이는** 방향의 오류입니다. 아직 실측 전이므로 아래
6번에 검증 계획을 넣었습니다.

### ③ 임계값을 정할 근거 데이터가 없습니다

유사도 컷을 0.6에 둘지 0.7에 둘지 정해야 하는데, 이를 정할 실데이터가 없습니다.
`feature/hub` README에도 같은 취지가 적혀 있습니다 — *"실제 운영 데이터 없이 정한
값이라 테스트하며 조정 필요"*. 학습 데이터가 없어 ML을 배제했던 것과 동일한 문제가
임계값 튜닝에서 되살아납니다. 코드 대조에는 임계값이 없습니다.

### ④ 팀이 내건 원칙과 더 잘 맞습니다

`CLAUDE.md`의 원칙은 "설명 가능한 추천 구조", "병원 적합도 매칭은 AI 미사용"입니다.
구급대원에게 제시할 근거가 **"혈전제거술 가능 → 통과"** 인 편이 **"유사도 0.82점"**
보다 낫고, 심사에서도 **안전이 걸린 배제를 규칙으로 처리한 것은 강점**으로 설명할 수
있습니다.

### ⑤ 상류에서 고칠 문제를 하류에서 덮고 있습니다

임베딩 도입 근거는 "voice의 LLM 출력이 자유 텍스트라 문자열 매칭이 불안정하다"였고,
진단 자체는 정확합니다. 다만 **LLM은 고정된 라벨 집합 중 고르게 하면 안정적으로
수행합니다**(structured output / enum 제약). voice에서 코드로 내보내면 하류의 유사도
계산이 불필요해집니다.

## 3. 무엇을 바꾸는가

### 목표 구조

```
voice : LLM 자유 텍스트 ──[LLM 분류]──→ 표준 코드  (필요역량)
info  : 병원 제각각 표기 ──[임베딩]───→ 표준 코드  (보유역량)
hub   : 코드 ↔ 코드 정확 대조 (임계값 없음, 결정적)
```

AI는 양 끝단에서 한 번씩만 돌고, **가운데 판정은 순수 규칙**입니다. 판정은 두 층으로
나눕니다.

| 층 | 방식 | 대상 |
|---|---|---|
| 하드필터 (없으면 탈락) | 코드 정확 대조 | 시술 가능 여부, 병상 종류, 응급실 운영 여부 |
| 소프트 점수 (순위) | 기존 가중합 유지 | 거리, 병상 수, 의사 수, 당직 ETA |

임베딩 점수는 하드필터에 넣지 않습니다. 남기더라도 동점 처리 보조까지입니다.

### 스키마 변경 — 기존 필드는 그대로, optional 추가만

```json
{
  "hospitalId": "H001",
  "name": "○○병원",
  "gps": { "lat": 35.1795, "lng": 128.1076 },

  "availableBedCount": 12,
  "bedsByType": {
    "ER_ADULT": 10,
    "ER_PEDIATRIC": 2
  },

  "nightDutyAvailable": true,
  "capabilities": [
    "PROC_IV_THROMBOLYSIS",
    "PROC_EVT_THROMBECTOMY"
  ],

  "specialties": [
    {
      "department": "흉부외과",
      "doctorCount": 3,
      "recentProcedureTags": ["기흉", "흉부외상"]
    }
  ],
  "source": "rule",
  "updatedAt": "2026-07-29T10:00:00Z"
}
```

| 필드 | 상태 | 설명 |
|---|---|---|
| `bedsByType` | **신규 (optional)** | 병상 종류별 가용 수. 소아/성인 분기의 핵심 |
| `capabilities` | **신규 (optional)** | 표준 역량 코드 목록. 하드필터 대조 대상 |
| 그 외 전부 | 유지 | 변경 없음 |

추가 필드는 전부 optional이라 **hub가 당장 읽지 않아도 아무것도 깨지지 않습니다.**

### 어휘 범위 — 처음에는 최소로

44개 전체를 강제하지 않습니다. **시연 시나리오 3개에 실제로 필요한 코드만 10개
안쪽**으로 시작하고, 나머지는 목록으로만 둡니다. 어휘 정의와 검증 함수는 info가
작성해 제공합니다.

## 4. 브랜치별 작업 변동과 난이도

| 브랜치 | 변경 내용 | 난이도 | 예상 | 기존 코드 |
|---|---|---|---|---|
| `feature/dashboard` | **없음** | — | — | 무변동 |
| `feature/voice` | 프롬프트에 코드 목록 추가 + enum 검증. 기존 자유 텍스트 필드는 **그대로 유지하고 코드 필드만 병기** | 낮음 | 0.5일 | 삭제 없음 |
| `feature/hub` | 스코어링 **앞에** 코드 대조 프리필터 한 겹 추가. `specialty_matcher` · `scoring` · `geo` · `delivery` 전부 유지 | 중간 | 1일 | **삭제 없음, 추가만** |
| `feature/info` | E-Gen → 표준 코드 정규화 매퍼 구현 | 큼 | 2~3일 | 미구현 영역이라 순증 아님 |

작업량 대부분이 info로 떨어지며, 이는 어차피 구현해야 할 영역입니다. hub는 이미
검증이 끝난 `hub_engine` / `specialty_matcher` / `delivery` 를 그대로 두고 진입점에
필터만 얹습니다.

### 명시적으로 안 건드리는 것

- 승인 액션 처리(`apply_approval_action`) 및 수신 주체 = hub 확정 — 유지
- 병상 갱신 알림(hub → info) — 유지
- 존(Zone) 로직, 거절 비율 기반 확장 — 유지
- 통합 매칭 결과 스키마(hub → dashboard) — 유지
- `specialtyMatch.score` 노출 — 유지 (설명용으로 계속 유효)

## 5. 리스크

- **가장 큰 의존은 voice입니다.** 코드 어휘를 내보내주지 않으면 구조가 성립하지
  않습니다. info가 어휘 목록 · 검증 함수 · 예시를 완성해 전달하겠습니다.
- 마감이 촉박하므로 **어휘를 최소 범위로 고정**하고, 확장은 대회 이후로 미룹니다.
- 실측 결과가 예상과 다르면(임베딩이 신경과/신경외과를 잘 구분하면) 이 제안의 ②번
  근거는 철회합니다. 다만 ① ③ ④ 는 그대로 유효합니다.

## 6. 결정 전 검증 (30분)

주장 ②는 아직 추정이므로, hub가 쓰는 동일 모델
(`paraphrase-multilingual-MiniLM-L12-v2`)로 아래 유사도를 직접 측정해 근거로
제시하겠습니다.

| 질의 (voice 출력 형태) | 비교 대상 | 확인하려는 것 |
|---|---|---|
| `"급성 허혈성 뇌졸중"` | `신경과` / `신경외과` | 둘 다 높게 나오면 이 판정을 임베딩으로 할 수 없음 |
| `"심근경색"` | `순환기내과` / `심혈관센터` / `CV Lab` | 표기 변형에 얼마나 버티는지 |
| `"소아 열성경련"` | `소아청소년과` / `응급의학과` | 소아 분기가 이름만으로 잡히는지 |

**측정 결과를 먼저 공유한 뒤 확정 논의**를 제안합니다.

## 7. 요청 사항

1. **hub** — 프리필터 한 겹 추가 가능 여부 (기존 로직 유지 전제)
2. **voice** — 출력에 코드 필드 병기 가능 여부 (자유 텍스트 유지 전제)
3. 위 두 가지 확정 시, info가 어휘 목록 v1(10개 내외)을 당일 배포

## 부록 · 별건 확인 요청

`CLAUDE.md`에 `hv1`(전문의 보유) / `hvec`(병상 현황) / `hv2`(중증질환 수용)가 **세 개의
API**로 기재돼 있습니다. 제 이해로는 이는 별도 API가 아니라 E-Gen 실시간 가용병상
조회 **응답 안의 필드명**입니다. 사실이라면 문서 정정이 필요하고, 호출 횟수 · 주기
설계도 달라집니다. API 키 승인 후 실제 응답을 찍어 정정 내용을 공유하겠습니다.

> **일정 리스크**: 공공데이터포털 E-Gen 활용신청이 아직 미신청 상태입니다. 승인이
> 지연되면 info 쪽 실데이터 연동이 전부 mock으로 밀립니다. 금일 신청 예정입니다.
