## 1. 브랜치의 역할과 시스템 내 위치

### 1.1 한 문장 정의

응급의료기관의 상태를 모아 **표준 형식(`HospitalInfo`)으로 정규화해 `feature/hub`에
공급**한다. **환자에게 어느 병원이 적합한지는 판정하지 않는다** — 그건 hub의 몫이다.

이 경계가 설계 전반을 지배한다. info는 "이 병원이 지금 어떤 상태인가"와 "그 정보를
얼마나 믿을 수 있는가"까지만 답하고, "그래서 이 환자를 어디로 보낼 것인가"는 거리와
환자 정보를 가진 hub가 결정한다.

### 1.2 데이터 흐름

```
[경로 A] E-Gen 공개 API (전국 실시간, 얕음)
    ├─ getEgytListInfoInqire                좌표 · 기관 등급
    ├─ getEmrrmRltmUsefulSckbdInfoInqire    실시간 가용병상 6종 · 장비 가용
    └─ getSrsillDissAceptncPosblInfoInqire  중증질환 수용가능 28항목

         │        → HospitalInfo ─────────────────────────────┐
         │                                                     │
         └─[축적] 가공 전 원본을 시계열로 저장 (snapshot.py)     │
                  data/snapshots_nationwide/YYYY-MM-DD.jsonl   │
                       │                                       │
                       ↓                                       │
[경로 C] 신뢰도 진단·외부 대조 (hospital_score/)                │
    ├─ 심평원 병원정보 (15001698)         ykiho · 좌표          │
    ├─ 심평원 의료기관별상세 (15001699)   전문과목별 전문의 수   │

         │                                                     │
         └─[규칙] 좌표 최근접 조인 → 계층 기반 점수              │
                  → assessment (여건 + 15그룹 역량 + 신뢰도 + 근거)
                                                               │
[경로 B] 병원 서류 이미지 (정적, 깊음)                          │
    ↓[AI] 레이아웃 검출 → 영역별 텍스트 인식                     │

    DocumentFields ──→ (병합 미구현) ────────────────────────────┤
                                                               ↓
                                                         feature/hub
```

### 1.3 세 경로의 성격

| | 경로 A — E-Gen | 경로 B — 서류 OCR | 경로 C — 신뢰도 진단 |
|---|---|---|---|
| 폴더 | `Hospital_inform/` | `ocr/` | `Hospital_inform/info/hospital_score/` |
| 질문 | 정보를 어디서 가져오나 | 공개 API가 못 주는 것 | **가져온 정보를 믿을 수 있나** |
| 범위 | 전국 533곳 | 소수 기관 | 전국 533곳 |
| 실시간성 | 실시간 | 정적(서류 발급 시점) | 실시간 + 정적 대조 |
| 처리 | 규칙 기반 | AI(검출·인식·추출) + 규칙(검증) | 규칙 기반 |
| 상태 | **실 API 연동 완료** | 로직 완성 · 실측 대기 | **구현 완료 · hub 연동 대기** |

**CLAUDE.md "핵심 AI 활용 원칙" 기준 구분**: 경로 A·C는 전부 규칙 기반(`source: "rule"`),
경로 B는 값을 **찾아내는 일만** AI가 하고 그 값을 받아들일지는 전부 규칙이 정한다
(`source: "ai"` + `grounded` 플래그).

### 1.4 담당하지 않는 것 (명시적 제외)

- **병원 매칭·존(Zone) 로직** → `feature/hub`로 이관 확정
- **승인 액션 수신**(hospital_approve/reject/final_approval) → `feature/hub`가 수신
- **환자 바이탈 정보** → 사용하지 않기로 결정, 관련 스키마 전부 제거
- **dashboard와의 직접 통신** → dashboard는 hub와만 통신

## 3. 사용한 외부 API 전체

### 3.1 E-Gen — 국립중앙의료원 전국 응급의료기관 정보 조회 서비스

- 포털 등록번호 **15000563**, 기본 주소 `http://apis.data.go.kr/B552657/ErmctInfoInqireService`
- 서비스키 승인 **2026-08-10**, `.env`의 `EGEN_SERVICE_KEY`
- 응답 포맷 **XML** (표준 라이브러리 `xml.etree.ElementTree`로 파싱 — 의존성을 늘리지 않음)

| 오퍼레이션 | 얻는 것 | 호출 파라미터 | 주기 |
|---|---|---|---|
| `getEgytListInfoInqire` | 좌표(`wgs84Lat/Lon`), 기관 등급(`dutyEmclsName`) | `Q0`/`Q1` | **하루 1회** (거의 안 변함) |
| `getEmrrmRltmUsefulSckbdInfoInqire` | 실시간 가용병상 6종, 총병상(`hvs38`), 입력시각(`hvidate`), 장비 가용 | `STAGE1`/`STAGE2` | 매 주기 |
| `getSrsillDissAceptncPosblInfoInqire` | 중증질환 수용가능 `MKioskTy1`~`MKioskTy28` | `STAGE1`/`STAGE2` | 매 주기 |

**호출량 설계** — 개발계정 일일 한도가 있어 두 가지로 절약했다.

1. **시도 인자를 비우면 전국이 1회 호출로 온다.** 자치구 25번 나눠 부를 필요가 없다.
   전국 스냅샷의 호출 횟수가 서울만 받을 때와 **동일**하다.
2. **좌표·등급은 하루 1회만.** 20분 주기 기준 하루 **145회** (= 72 × 2 + 1).

**구현상 주의점 3가지** (`egen/client.py`)

- **HTTP 200으로 오는 오류.** 인증 실패·트래픽 초과는 봉투 자체가 `<response>`가 아니고,
  서비스 오류는 봉투는 같고 `resultCode`만 다르다. `raise_for_status()`만 믿으면 오류
  응답을 정상 데이터로 착각한다 → `_parse()`에서 두 종류를 모두 검사한다.
- **서비스키 이중 인코딩.** 인코딩/디코딩 두 종류로 발급되는데, 인코딩된 키를 그대로
  넘기면 `requests`가 다시 인코딩해 인증에 실패한다. `%`가 있으면 `unquote()` 한다.
- **빈 지역 인자는 아예 보내지 않는다.** 빈 문자열을 보내면 "그 이름의 시군구"를 찾아
  0건이 되는 경우가 있어, 생략과 같지 않다.

### 3.2 심평원(HIRA) — 신고와 대조할 외부 근거

- **서비스키는 E-Gen과 같은 값이다.** data.go.kr은 계정당 인증키가 하나이고 서비스별
  활용신청만 따로 필요하다. `.env`에 `HIRA_SERVICE_KEY` 한 줄 추가.
- 일일 트래픽 800,000회로 여유가 크다.

| 데이터 | 확정 경로 | 포맷 | 얻는 것 |
|---|---|---|---|
| 병원정보 (15001698) | `apis.data.go.kr/B551182/hospInfoServicev2/getHospBasisList` | XML | `ykiho` · 좌표 · 총 의사 수 — **조인의 출발점** |
| 의료기관별상세 (15001699) | `apis.data.go.kr/B551182/`**`MadmDtlInfoService2.8`**`/` 11종 | JSON | **전문과목별 전문의 수** · 진료과목 · 장비 등 |
| 전문병원 지정 현황 (15051054) | `api.odcloud.kr/api/15051054/v1/uddi:c154ba0c…` | JSON | 분야별 전문병원 **114곳** |

**⚠️ 엔드포인트 버전 함정 — 여기서 몇 시간을 날렸다.**

구버전 `MadmDtlInfoService2.7`도 게이트웨이에 **실재해서 403(권한 없음)을 돌려준다.**
이걸 보고 "경로는 맞고 승인만 안 났다"고 오진하기 쉽다.

data.go.kr 게이트웨이는 경로를 **서비스 + 오퍼레이션 전체로 검증**한다:

```
400 NO_OPENAPI_SERVICE             = 그런 경로가 없다
403 SERVICE_KEY_IS_NOT_REGISTERED  = 경로는 실재하나 이 키에 권한이 없다
```

**403은 "그 경로가 실재한다"만 알려줄 뿐 "그게 현재 버전이다"라는 뜻이 아니다.**
버전은 반드시 포털 마이페이지 활용신청 상세 화면의 **End Point** 줄로 확인해야 한다.
`hira.py`는 이 둘을 별도 예외(`HiraNotApprovedError` / `HiraApiError`)로 나눠, 다음에
같은 함정에 빠지지 않도록 오류 메시지에 확인 절차를 적어 두었다.

**부수 효과**: 상세정보서비스의 모든 오퍼레이션은 `ykiho`를 입력으로 받는데, 없이
부르면 오류가 아니라 정상 응답에 `totalCount=0`이 온다 — 조용히 빈 결과가 되므로 주의.

### 3.3 Supabase — 대체 DB 2개 프로젝트

| 프로젝트 | 테이블 | 용도 | 환경변수 |
|---|---|---|---|
| 병원용 | `hospitals` | E-Gen 승인 전 대체 DB. **현재는 병상(`hvec`) 읽기·쓰기 전용** | `SUPABASE_URL` / `SUPABASE_KEY` |
| 구급차용 | `ambulances` | 구급차 레지스트리(apid/name/gps/voicePort) | `AMBULANCE_SUPABASE_URL` / `AMBULANCE_SUPABASE_KEY` |

**병상만 Supabase에 남긴 이유**: E-Gen은 **조회 전용 공개 API**라 hub가 이송 확정
(`final_approval`) 시 차감한 병상 수를 되돌려 쓸 방법이 없다
(`HttpEgenClient.update_bed_count()`가 `NotImplementedError`인 이유). 병상까지 실 API로
읽으면 30분마다 재조회할 때 hub의 차감이 리셋돼 **뺑뺑이 방지 취지와 정반대**로 간다.

→ 이 구조가 §8의 "hub로 7곳만 흐르는 문제"의 직접 원인이며, 합의로 해소된다.

### 3.4 세 가지 클라이언트 구현 (교체 가능 구조)

`EgenClient` Protocol 하나에 구현이 셋이다. 쓰는 쪽은 어느 것인지 몰라도 된다.

| 구현 | 출처 | 쓰임 |
|---|---|---|
| `FixtureEgenClient` | 미리 만든 JSON 파일 | API 키 없이 개발 (쓰기는 no-op) |
| `SupabaseEgenClient` | Supabase `hospitals` 테이블 | 병상 읽기·쓰기 |
| `HttpEgenClient` | 진짜 E-Gen API | 목록·좌표·중증질환 |

반환값은 전부 **"응답 봉투를 벗긴 원본 필드명 그대로의 딕셔너리 목록"**이다
(`hpid`, `hvec`, `dutyName` …). 이름을 바꾸는 일은 전적으로 매퍼가 한다 —
모델/API 호출부와 비즈니스 로직을 분리하라는 CLAUDE.md 원칙의 적용이다.

## 4. 경로 A — E-Gen 정규화 구현

`egen/mapper.py`가 이 브랜치의 본체다. 하는 일은 셋이다.

### 4.1 합치기

E-Gen은 필요한 정보를 오퍼레이션 3개에 나눠 준다. **가용병상 응답을 기준으로 돌면서**
목록정보(좌표)와 중증질환(시술 역량)을 `hpid`로 이어붙인다. 가용병상 응답에 없는 기관은
지금 응급실을 운영하지 않는다고 보고 다루지 않는다.

**좌표가 없으면 제외한다.** hub가 거리를 계산할 수 없어 후보에 넣는 의미가 없기
때문이다. 다만 조용히 사라지지 않고 `MappingReport.skipped_no_location`에 이름이 남는다.

### 4.2 결측 처리 — 여기가 진짜 일이다

E-Gen은 병원이 값을 입력하지 않으면 `-1`을 보낸다. 세 상태를 절대 뭉개지 않는다.

| 값 | 의미 | 처리 |
|---|---|---|
| `0` 이상 | 관측된 가용 병상 수. **`0`은 확인된 만실** | 그대로 |
| `-2` 이하 | **과밀** (정원보다 환자가 그만큼 많음) — 미입력이 아니라 관측값 | `clamp_available()`로 0, 원값은 리포트에 |
| `-1` / 필드 자체 없음 / 비수치 | 병원이 입력을 안 함 = **미상** | `None` → `bedsByType`에 **키를 넣지 않음** |

**미상을 표현하는 방식이 "키 없음"인 것이 핵심이다.** `{"ER_ADULT": 0}`은 만실을 뜻하므로
미상을 0으로 채우면 안 된다. `availableBedCount`(hub 기존 필드, `ge=0`)에는 보수적으로
0을 넣되, hub가 `bedsByType`의 키 유무로 "미상"과 "확인된 만실"을 재해석한다.

> **실측으로 잡은 버그**: 과거 매퍼가 `-1` 이하를 전부 미상 처리해서, **가장 갈 수 없는
> 병원(과밀 -24)이 "모르는 병원"이 되고 있었다.** 서울 55곳 중 6곳이 해당했고 전부
> 상급종합병원이었다.

### 4.3 입력 오류 걸러내기

임의의 상한을 두는 대신 **그 병원이 신고한 총 병상(`hvs38`)을 상한**으로 쓴다.
국립중앙의료원이 거의 전 필드에 `12312` 같은 시험값을 넣어 두고 있어, 그대로 두면
대시보드에 "중환자실 12,308석"이 뜬다. 버린 값은 `implausible_beds`에 남는다.

### 4.4 3상태 유지

중증질환 값의 실제 어휘는 **`Y` / `불가능` / `정보미제공` 3종**이다(명세의 `N`은 쓰이지
않는다). `Y`에는 뒤쪽 공백이 붙어 온다(`'Y         '`). "안 된다"와 "모른다"를 뭉개면
hub가 근거를 설명할 수 없으므로 `clean_flag()`가 `True`/`False`/`None` 3상태를 유지한다.

### 4.5 매핑표 (실측으로 전부 확정 — `[추정]`이 하나도 없다)

**병상 6종** — 어휘의 코드가 전부 채워진다.

| 코드 | E-Gen 필드 | 신고 병원 (서울 55곳 중) |
|---|---|---|
| `ER_ADULT` | `hvec` 일반 | 55 |
| `ER_PEDIATRIC` | **`hv28`** 소아 | 23 |
| `ER_NEGATIVE` | `hv29` 응급실 음압격리 | 37 |
| `ICU` | `hvicc` [중환자실] 일반 | 35 |
| `CCU` | `hv34` [중환자실] 심장내과 | 12 |
| `OR` | `hvoc` [기타] 수술실 | 54 |

> **실측으로 잡은 버그 2**: `hv11`을 소아 병상으로 매핑해 뒀는데 실제로는 **인큐베이터
> 보유 여부(Y/N)**였다. `int('Y')`가 실패해 소아 병상이 늘 미상이었다. 진짜 필드는 `hv28`.

**시술·장비 역량 7종**

| 코드 | 출처 | 보유 병원 (서울 55곳 중) |
|---|---|---|
| `EQP_CT_24H` | `hvctayn` (가용병상 응답) | 54 |
| `EQP_ANGIO_SUITE` | `hvangioayn` (가용병상 응답) | 38 |
| `PROC_PCI_EMERGENCY` | `MKioskTy1` 심근경색 재관류 | 33 |
| `PROC_CRANIOTOMY` | `MKioskTy3`, `MKioskTy4` 뇌출혈 수술 | 31 |
| `PROC_EVT_THROMBECTOMY` | `MKioskTy2` 뇌경색 재관류 | 29 |
| `PROC_CESAREAN_EMERGENCY` | `MKioskTy17` 산과수술 | 22 |
| `PROC_IV_THROMBOLYSIS` | **대응 항목 없음** | **0** |

**마지막 줄이 서류 OCR(경로 B)의 존재 이유다.** tPA(정맥 혈전용해술)는 `MKioskTy` 28개
항목 어디에도 없어 공개 API로는 채울 수 없다. 뇌경색은 재관류중재술로만 표현되고 정맥
혈전용해술은 따로 묻지 않는다.

> 장비 가용 여부가 **가용병상 응답에 같이 온다**는 것을 확인해 연결한 결과, "역량 정보가
> 전혀 없는 병원"이 21곳 → **1곳**으로 줄었다.

### 4.6 파생 필드

- **`nightDutyAvailable`**: 공개 API에 당직 전문의 정보가 없어 **중증질환 수용가능을
  프록시**로 쓴다 — "재관류가 지금 가능하다"는 곧 해당 과 전문의가 대응 가능하다는 뜻.
- **`specialties[]`**: hub가 아직 `capabilities`를 안 읽고 **진료과명을 임베딩으로
  대조**하므로, 같은 근거로 진료과도 만들어줘야 매칭이 작동한다
  (`PROC_PCI_EMERGENCY` → 순환기내과 등). 장비 역량(`EQP_*`)은 넣지 않는다 — 진료과
  목록에 "CT"가 끼면 임베딩 매칭이 흐려진다. `doctorCount`는 0(공개 API에 인력 수 없음).

### 4.7 스키마 계약 검증 (`schema.py`)

이 파일의 목적은 **"잘못된 데이터가 만들어지는 순간 바로 실패시키는 것"**이다.
형식이 틀린 JSON을 hub에 보내면 통합 시점에야 터지는데 그때는 원인 찾기가 훨씬 어렵다.

| 검사 | 잡는 것 |
|---|---|
| `extra="forbid"` | `availableBedcount` 같은 오타. hub는 모르는 필드를 무시해 조용히 기본값이 들어감 |
| 좌표 범위 (위도 33~39.5, 경도 124~132) | 위도·경도를 바꿔 넣은 실수 (국내 좌표는 반드시 범위를 벗어남) |
| 병상 코드 어휘 검사 | 어휘에 없는 코드, 음수 병상 수 |
| 역량 코드 어휘 검사 | voice의 "필요역량"과 info의 "보유역량"이 같은 어휘여야 hub가 대조 가능 |
| ISO 8601 검사 | `updatedAt` 형식 파손 |

**어휘를 작게 유지하는 것이 원칙이다** — 병상 6종 + 역량 7종. voice 담당자가 외울 수
있어야 합의가 빨라진다는 판단이며, 확장은 대회 이후로 미뤘다.

### 4.8 시계열 축적 (`snapshot.py`)

E-Gen은 **"지금 값"만 주고 과거 이력을 주지 않는다.** 나중에 몰아서 받을 방법이 없으므로
지금부터 직접 찍어 쌓는 수밖에 없다.

- **가공하지 않은 원본 행을** 하루 1파일 JSONL에 append한다. 가공본만 남기면 매핑
  해석을 고칠 때마다 지난 데이터가 죽는다.
- **호출 실패도 한 줄로 남긴다.** "그 시각에 데이터가 없다"와 "호출이 실패했다"는 다르고,
  나중에 빈 구간을 볼 때 이 구분이 없으면 원인을 알 수 없다.
- 상주 실행 중 강제 종료돼도 직전 관측까지는 남도록 매 줄 `flush()` 한다.

| 폴더 | 범위 | 주기 | 기간 |
|---|---|---|---|
| `data/snapshots/` | 서울 55곳 | 10분 | 2026-08-10 ~ 08-12 (중단) |
| `data/snapshots_nationwide/` | 전국 443곳 | 20분 | 2026-08-12 ~ (**가동 중**) |

전국이 서울을 포함하므로 서울만 보려면 `hpid` 접두어 `A11`로 거른다.
Windows 작업 스케줄러에 `snapshot_nationwide.bat`을 등록해 상시 수집한다.

## 5. 경로 C — 신뢰도 진단과 외부 대조

### 5.1 왜 만들었나 — 실측 하나가 계기였다

```
전국 가용병상 1위  한림대학교한강성심병원  30병상
                  → 2019년 11월 19일에 입력된 값 (2,457일 전)
                  → 게다가 국내 대표 화상 전문병원인데 [중증화상] 항목은 "정보미제공"
```

E-Gen이 주는 값은 전부 **병원이 스스로 신고한 것**이고, **같은 소스 안에서는 그게 맞는지
검증할 방법이 없다.** 그래서 소스를 늘려 어긋나는 지점을 드러낸다.

### 5.2 실측 결과 (재현: `python -m hospital_score.report`, API 호출 0회)

**① 피드가 죽은 병원이 전국 25곳, 최대 8.6년**

| 마지막 갱신 | 경과 | `hvec` | 병원 |
|---|---|---|---|
| 2018-01-02 | 3,144일 | 5 | 에이치제이매그놀리아국제병원 |
| 2018-05-03 | 3,022일 | 10 | 강남고려병원 |
| **2019-11-19** | **2,457일** | **30** | **한림대학교한강성심병원** |

**25곳 전부가 `응급실운영신고기관`이다.** 서울 4곳에서 처음 발견했을 때 등급과 100%
일치했는데 전국으로 넓혀도 예외가 없다. 병상 API에 등장하는 응급실운영신고기관 27곳 중
**25곳(93%)이 방치 상태**다.

**② 그 유령 값이 전국 가용병상 1위다**

```
30병상   2,457일 방치   한림대학교한강성심병원   ← 1위
28병상   6분 전 갱신     인제대학교일산백병원
24병상   5분 전 갱신     충북대학교병원
```

2위부터는 전부 10분 이내 갱신이다. **오염된 것은 정확히 정렬 맨 윗칸 하나**이고,
hub가 `availableBedCount`로 순위를 매기기 시작하면 역량 최하위 기관이 병상 최상위가 된다.

**③ 미상이 하위 등급에 계단식으로 몰려 있다** (438곳 × 28항목 = 12,264칸)

| 등급 | 병원 | 가능 | 불가능 | 정보미제공 |
|---|---|---|---|---|
| 권역응급의료센터 | 44 | 74.5% | 4.1% | **21.4%** |
| 지역응급의료센터 | 139 | 45.8% | 1.2% | **53.0%** |
| 지역응급의료기관 | 231 | 10.9% | 0.9% | **88.2%** |
| 응급실운영신고기관 | 24 | 3.6% | 0.0% | **96.4%** |

전체 미상 **70.8%**. `dutyEmclsName`(등급) 하나가 신고 성실도를 거의 그대로 설명하는데,
**이 필드는 E-Gen 목록정보에 이미 오면서 지금 파이프라인 어디에서도 쓰이지 않는다.**
미상률이 높은 항목은 소아 3종과 중증화상(88.4%) — **희소 역량일수록 아무도 신고하지 않는다.**

**④ 명부에는 있는데 응답에 아예 없는 병원 90곳**

| 등급 | 명부 | 병상 API | 중증질환 API |
|---|---|---|---|
| 권역응급의료센터 | 44 | 44 | 44 |
| 지역응급의료센터 | 139 | 139 | 139 |
| 지역응급의료기관 | 234 | 233 | 231 |
| 응급실운영신고기관 | 116 | **27** | **24** |

이 병원들은 "병상이 0"이 아니라 **응답에 등장하지 않는다.**

**⑤ 신고끼리 어긋나는 칸**

소아 항목 5종에만 `MKioskTy*Msg` 동반 필드가 있고(활용가이드에 없던 것, 실측으로 발견),
내용은 "0세 이상", "최저체중:400g" 같은 연령·체중 조건 자유텍스트다. 정보미제공 1,935칸 중
206칸(10.6%)에 조건 메시지가 있고, **그중 22칸은 메시지가 아예 `불가능`이다** — 값은
"모른다"인데 메시지는 "못 받는다"인 셈이다.

**⑥ 전문병원으로 지정된 역량이 신고에는 없다**

| 지정분야 | 지정 | 명부 매칭 | 신고 상태 |
|---|---|---|---|
| **화상** | 5 | 4 | **가능 0** · 정보미제공 2 · 응답없음 2 |
| 수지접합 | 6 | 5 | 가능 2 · 정보미제공 1 · 응답없음 2 |
| 뇌혈관 | 4 | 4 | 가능 3 · 정보미제공 1 |
| 심장 | 1 | 1 | 가능 1 |

**국내 화상 전문병원 5곳 중 E-Gen에서 화상 역량이 보이는 곳이 하나도 없다.** 그리고
미신고 2곳(한강성심 2,457일 · 베스티안 565일)은 ①의 피드 사망 명단에도 들어 있다 —
같은 병원에서 ①역량 미신고 ②병상 값 수년째 방치 ③그 방치된 값이 전국 1위로 정렬됨이
겹친다.

> 지정은 "그 분야 전문성을 인증받았다"이지 "지금 받을 수 있다"가 아니므로, 신고하지
> 않은 것 자체가 곧 오류는 아니다. 다만 **E-Gen만 보는 매칭 엔진은 화상 환자에게 이
> 5곳을 후보로 올리지 못한다**는 사실은 그대로 남는다.

### 5.3 E-Gen ↔ 심평원 조인 — 좌표 최근접

두 기관에 공통 식별자가 없다(`hpid` ↔ `ykiho`). 요양기관기호도 사업자번호도 목록정보에
없어 **좌표 최근접(haversine)**으로 붙인다. 심평원 병원급(상급종합 47 · 종합병원 338 ·
병원 1,433 = 1,818곳)을 받아 대조한 결과:

| 거리 | 매칭 | 비율 |
|---|---|---|
| 100m 이내 | 490/533 | 91.9% |
| 300m 이내 | 512/533 | 96.1% |
| **1.2km 이내 (채택)** | **518/533** | **97.2%** |

**오차 중앙값 11m.** 미매칭 15곳은 전부 보건의료원·보건지소로, 병원급만 조회한 탓이지
매칭 실패가 아니다.

- **기관명 정규화만으로는 92.7%였다.** `의료법인대산의료재단익산병원` ↔ `익산병원`처럼
  같은 병원인데 표기가 달라 놓치는 것들이 있다.
- 그래서 **좌표가 없는 데이터(전문병원 지정 현황)는 기관명으로 붙일 수밖에 없고, 그
  결과는 하한으로 읽어야 한다.**
- 1.2km라는 잣대는 `send_to_hub.py`의 Supabase 대응표 검증과 **같은 기준**이다.

**재현성 확인**: 캐시를 치우고 처음부터 재생성해 대조한 결과 조인 518곳이 **내용까지
동일**했고, 전문의 수는 오히려 3곳 늘었다(이전 실행에서 커넥션 오류로 놓친 곳들).
`--build-join`은 재시도 3회 · 25곳마다 중간저장 · 이어받기를 한다.

## 6. 점수 산정 — 원리와 근거

### 6.1 설계 전제 — 세 가지 제약이 형태를 결정했다

**(1) 정답이 없다.** "이 병원이 이 환자를 실제로 받았는가"의 라벨이 없다. 대용 정답도
전부 부족하다 — 병원의 `불가능` 신고는 전체의 1.2%인 데다 그건 우리 **입력**이지 정답이
아니고, 전문병원 지정은 5개 분야뿐이다. **그래서 가중치를 최적화하지 않는다.** 근거 없이
`0.73` 같은 값을 두면 임의값에 정밀함의 외양만 입히는 것이다.

**(2) 실패 비용이 비대칭이다.** 받을 수 있는 병원을 후보에서 빼는 것(골든타임 손실)이,
못 받는 병원을 올리는 것(전화 한 번 더)보다 훨씬 나쁘다. **애매하면 남긴다.**

**(3) 병원당 단일 점수는 만들지 않는다.** 심근경색 환자와 화상 환자에게 같은 병원의
수용가능성이 다르다.

### 6.2 산출물 구조 — 두 축 + 신뢰도 + 근거

```
hospitalId / name / emcls
├─ conditions   여건 스칼라 — 환자와 무관 (병상·과밀·피드 신선도)
├─ capabilities 역량 벡터 — 15그룹, 환자에 따라 다름
├─ evidence     판정에 실제로 쓰인 근거 (기계 판독용)
└─ (각 그룹) status / tier / score / confidence / basis / items
```

**핵심 원칙 1 — `score`와 `confidence`를 곱하지 않는다.** 섞으면 **"확실히 낮음"과
"모르겠음"이 구분되지 않는다.** 미상과 확인된 만실을 구분해온 기존 원칙(`bedCountUnknown`)과
같은 논리다. 끝까지 별도 필드로 나간다.

**핵심 원칙 2 — 여건과 역량을 합치지 않는다.** 병상이 꽉 찬 화상 전문병원과 병상이 남는
일반병원 중 누구를 택할지는 환자와 거리에 따라 다르다.

**핵심 원칙 3 — 절대값은 info가 정하지 않는다.** "2km 가깝지만 근거가 약한 병원 vs
5km 멀지만 확실한 병원"의 트레이드오프는 **거리를 가진 hub가 결정**한다.
info는 **순서와 근거만** 준다.

### 6.3 역량 점수 — 근거 강도 5계층

`score`의 전부다. 값 자체에 의미를 두지 않고 **순서만** 쓴다. `score = tier / 5`.

| tier | 라벨 | 조건 | `score` | `status` | `confidence` |
|---:|---|---|---:|---|---|
| 1 | `declared_no` | 병원이 "불가능" 신고 | **0.2** | `unavailable` | high |
| 2 | `unknown_bare` | 정보미제공 + 뒷받침 근거 없음 | **0.4** | `unknown` | low |
| 3 | `unknown_specialist` | 정보미제공 + 해당 진료과 전문의 보유 | **0.6** | `unknown` | low |
| 4 | `unknown_designated` | 정보미제공 + 그 분야 전문병원 지정 | **0.8** | `unknown` | medium |
| 5 | `declared_yes` | 병원이 "가능" 신고 | **1.0** | `available` | high |

#### 이 표에서 가장 중요한 한 줄: **불가능(0.2) < 근거 없는 미상(0.4)**

직관적으로는 "모르는 것"이 최하위 같지만, 그렇게 두면 **정보 미제공 병원이 명시적 거부
병원보다 아래로 밀린다.** 미상이 전체 70.8%이고 하위 등급일수록 심하므로(96.4%),
미상을 최하위로 두면 하위 등급 병원 대부분이 후보에서 사라진다 — 뺑뺑이를 줄이려는
목적과 정반대다. 불변식 검사가 이 성질을 직접 강제한다.

#### 왜 전문의가 "한 칸"만 올리나

- `ITEM_TO_DEPARTMENTS` 매핑표는 **우리가 세운 것이고 외부 근거로 검증되지 않았다.**
- 심평원 진료과가 **대분류만** 온다 — `순환기내과` 없이 `내과`. 특정성이 매우 낮다.
- 실측: **`불가능`이라 신고한 칸의 91.2%도 해당 진료과 전문의를 갖고 있었다.**

즉 전문의 유무는 역량의 증거로는 약하다. 그래서 점수를 **올리는** 근거가 아니라
**"역량 없음으로 단정하지 못하게 막는 하한"**으로만 쓴다. tier 3이 tier 2 바로 위
한 칸이고, `confidence`가 tier 2와 똑같이 `low`인 이유이기도 하다.

### 6.4 항목 하나의 판정 순서

```
신고값이 'Y'       → tier 5  basis = ["병원 신고: 수용 가능"]        [즉시 확정]
신고값이 '불가능'   → tier 1  basis = ["병원 신고: 수용 불가"]        [즉시 확정]
그 외(정보미제공/누락) ↓
    basis = ["병원 신고 없음(정보미제공)"]
    ① 그 항목을 포함하는 전문병원 지정분야를 갖고 있나?
         → tier 4  basis += "전문병원 지정: 화상"
    ② 그 항목에 필요한 진료과 전문의가 1명 이상인가?
         → tier 3  basis += "정형외과 전문의 12명"
    ③ 둘 다 아니면
         → tier 2  basis += "뒷받침할 외부 근거 없음"
```

**순서가 중요하다.** 전문병원 지정이 더 높은 tier이므로 전문의보다 먼저 확인한다.
**신고값 우선은 절대적이다** — 화상 전문병원이 "불가능"이라 신고했으면 tier 1이다.
지정은 "전문성을 인증받았다"이지 "지금 받을 수 있다"가 아니기 때문이다.

**전문병원 지정분야 → MKioskTy 항목 매핑**

| 지정분야 | 항목 | 지정분야 | 항목 |
|---|---|---|---|
| 화상 | 19 | 산부인과 | 16, 17, 18 |
| 수지접합 | 20, 21 | 주산기 | 15, 16 |
| 뇌혈관 | 2, 3, 4 | 소아청소년과 | 10, 12, 14 |
| 심장 | 1 | 안과 | 25 |

관절·척추·알코올처럼 중증질환 28항목에 대응이 없는 분야는 **일부러 비워뒀다** —
억지로 이으면 대조 결과가 오염된다.

### 6.5 그룹 점수 = 그룹 내 최댓값

15그룹은 MKioskTy 28항목 라벨의 **대괄호를 그대로 쓴 것**이다 — 우리가 임의로 묶지 않았다.

```
재관류중재술 · 뇌출혈수술 · 대동맥응급 · 담낭담관질환 · 복부응급수술
장중첩/폐색 · 응급내시경 · 저체중출생아 · 산부인과응급 · 중증화상
사지접합 · 응급투석 · 정신과적응급 · 안과적수술 · 영상의학혈관중재
```

**28번(응급실 Emergency gate keeper)만 그룹이 없다.** 중증질환 역량이 아니라 "응급실
자체를 운영하는가"를 묻는 항목이라 성격이 달라 벡터에서 뺐다 — 피드가 죽은 병원 중
이것만 `Y`인 곳들이 있다.

한 그룹에 항목이 여럿이면(예: `산부인과응급` = 분만/산과수술/부인과수술) **가장 높은
tier**를 택한다. 최솟값이나 평균이 아니다 — 실패 비용이 비대칭이라 보수적으로 낮추지
않는다. 단 `items` 필드에 **그룹 내 모든 항목의 원래 신고값이 그대로 남아**, "분만은
가능인데 부인과수술은 불가능"을 확인할 수 있다.

**연령축의 독립 근거**: `MKioskTy*Msg` 동반 필드를 가진 항목 5개가 영유아 집합과
**정확히 일치**한다 — 연령축이 우리 임의 분류가 아니라 E-Gen 자체 구조라는 증거다.
`vocabulary.py`는 이 성질을 import 시점에 assert로 검증한다.

**basis에 덧붙지만 점수를 바꾸지 않는 두 줄**: `stale`이면 "마지막 입력 N일 전",
그리고 "등급: 권역응급의료센터". **등급으로 점수를 올리면 사실상 "큰 병원 우대"가 되어
근거 강도만 반영한다는 원칙이 깨진다.** 등급별 미상률 차이는 데이터 품질의 관찰이지
역량의 증거가 아니다.

### 6.6 신뢰도 — 점수와 독립적인 축

| 상황 | confidence |
|---|---|
| 신고값 있음 (tier 1 또는 5) | `high` |
| 전문병원 지정 미상 (tier 4) | `medium` |
| 그 외 미상 (tier 2, 3) | `low` |
| 위 중 `high`인데 `stale`이면 | → `medium`으로 강등 |

강등 이유: **값은 있으나 언제 적힌 건지 믿기 어렵다.** 하루 넘게 갱신 없는 병원의
"가능" 신고는 값은 있어도 그 시점의 상태로 볼 수 없다.

### 6.7 여건 — 환자와 무관한 스칼라

| 필드 | 산출 | 의미 |
|---|---|---|
| `availableBeds` | `hvec` 파싱 | `-1`은 미입력이라 `None`, `-2` 이하는 **과밀이라 음수 그대로 보존** |
| `totalBeds` | `hvs38` | |
| `bedOccupancy` | `1 - max(0, avail)/total` | |
| `overcrowded` | `availableBeds < 0` | 정원 초과 수용 중 |
| `bedCountUnknown` | `availableBeds is None` | **"병상 0"과 다름** |
| `feedAgeMinutes` | `now - hvidate` (분) | |
| `stale` | 경과 > **1일** | |
| `missingFromFeed` | 응답 행 자체가 없음 | **"병상 0"과 절대 같지 않음** |

**`STALE_THRESHOLD = 1일`의 근거**: 실측 `hvidate` 갱신 경과 **중앙값 5분**, 443곳 중
**88.7%가 10분 이내**. 정상 분포가 이 정도이므로 하루는 충분히 이상값이다.

분석 단계에서는 과밀 **정도**(-24인지 -2인지)를 살려 음수를 그대로 두고, hub 전송
스키마가 음수를 막는 것은 mapper의 사정으로 분리했다.

### 6.8 근거(evidence) — 기계 판독용 대조값

```json
{
  "designatedFields": ["화상"],
  "specialists": {"성형외과": 8, "외과": 21, "정형외과": 12},
  "hvidate": "20260813011502",
  "equipment": {"CT": "Y", "ANGIO": "N"}
}
```

두 가지 의도적 제한이 있다.

1. **판정에 실제로 쓰인 진료과만 싣는다.** 심평원이 주는 26개 과 전부가 아니라
   판정 매핑에 등장하는 과만, 그중 인원 > 0인 것만. 근거는 "판단에 실제로 쓰인 것"이어야
   검증이 된다.
2. **원자료를 통째로 넘기지 않는다.** 넘기면 hub가 심평원 도메인 지식(진료과 코드
   체계·`ykiho`·전문병원 분야명)을 알아야 해석할 수 있게 되고, 그 지식이 hub에 복제되면
   **심평원 스키마가 바뀔 때 hub까지 깨진다** — 실제로 겪은 `2.7 → 2.8` 같은 일이 그렇다.

### 6.9 검증 — 정답이 없으므로 둘로 대신한다

**(a) 불변식** (`python -m hospital_score.scoring --check`)

라벨 없이 검증되고, 가중치를 어떻게 바꾸든 깨지면 실패다. *"이 순서만 안 깨지면 된다.
대부분의 파라미터 논쟁이 여기서 사라진다."*

```
계층 순서 4개:
  불가능 < 근거없는미상 < 전문의있는미상 < 전문병원지정미상 < 가능신고

산출물 검사 4개 (병원 × 그룹 전수):
  ① 미상이 어떤 경우에도 '불가능' 이하로 평가되지 않는다
  ② score가 tier/5와 정확히 일치한다 (다른 요인이 섞이면 즉시 검출)
  ③ basis가 비어 있는 항목이 없다 — "왜 이 병원인가"에 답할 수 없으면 실패
  ④ 신뢰도가 점수에 섞여 들어가지 않는다
```

**(b) 전문병원 지정 홀드아웃** (`--validate`)

전문병원 지정을 "정답"으로 감춰두고, 기존 방식(신고만 볼 때)과 새 점수가 각각 그 병원을
후보로 올릴 수 있는지 센다.

| 분야 | 지정·매칭 | 신고만 볼 때 | 새 점수 |
|---|---|---|---|
| **화상** | 4 | **0** | **4** |
| 수지접합 | 5 | 2 | 5 |
| 뇌혈관 | 4 | 3 | 4 |
| 산부인과 | 2 | 0 | 2 |
| 심장 | 1 | 1 | 1 |

**화상 전문병원은 기존 파이프라인에서 한 곳도 후보에 오르지 못한다.** 전부 "정보미제공"이라
존재하지 않는 것처럼 취급되기 때문이다. 표본이 작아(분야당 1~6곳) 정밀한 성능 측정은
안 되지만 **방향은 확실히 검증된다.**

### 6.10 무엇이 없어도 도는가

재료가 빠져도 죽지 않고 **판단의 근거가 약해질 뿐**이다. 재료가 없다고 멈추면 운영 중에
한 조각이 빠졌을 때 전체가 선다.

| 빠진 것 | 결과 |
|---|---|
| 거절 로그 | **점수 산정에 아무 영향 없다.** `scoring.py`는 `rejection.py`를 아예 읽지 않는다 |
| 심평원 캐시 | 533곳 그대로 산출되나 **미상이 전부 `unknown_bare`(0.4)로 떨어진다** |
| 전문병원 지정 캐시 | `report.py` 6절과 `--validate`만 건너뛴다 |
| 네트워크 | `report`·`scoring`은 전부 로컬 파일만 읽는다 |

> `data/`는 커밋되지 않으므로 **새 장비에서는 심평원 수집 명령 2개를 먼저 돌려야 한다**(§9).

```json
{

  "gps": { "lat": 37.5796, "lng": 126.9995 },

    { "department": "순환기내과", "doctorCount": 0,

```

| 필드 | 타입 | 비고 |

| `hospitalId` | string | **현재는 Supabase 체계 `S0000001`~`S0000007`** (§8에서 변경 예정) |
| `name` | string | |
| `gps.lat` / `gps.lng` | number | hub의 거리 계산에 그대로 쓰임. `lon`이 아니라 `lng` |
| `availableBedCount` | int ≥ 0 | 미상이면 0. **미상 여부는 `bedsByType` 키 유무로 구분** |
| `nightDutyAvailable` | bool | 중증질환 수용가능을 프록시로 씀 |
| `specialties[]` | object[] | hub의 임베딩 매칭 대상 |
| `source` | `"rule"` | 고정값 |
| `updatedAt` | ISO 8601 | `hvidate` 기반, 없으면 조회 시각 |
| `bedsByType` | dict (확장) | **미상인 종류는 키 자체를 넣지 않음** |
| `capabilities` | string[] (확장) | 역량 코드 7종. hub 하드필터 대조 대상 |

> **전송 방식**: 병원 1곳당 POST 1회. `to_hub_json()`이 `exclude_none=True`로 값 없는
> 선택 필드를 아예 빼서 보낸다.

### 7.3 ② info → hub : `AmbulanceInfo` (구급차 레지스트리)

```json
{
  "apid": "A0000001",
  "name": "구급 1호차",
  "gps": { "lat": 37.4979, "lng": 127.0276 },
  "voicePort": 6000,
  "source": "rule",
  "updatedAt": "2026-08-11T00:00:00Z"
}
```

- 병원용과 **별도의 Supabase 프로젝트**(`ambulances` 테이블)에서 같은 주기로 읽어 보낸다.
- credential이 없으면 **이 부분만 조용히 건너뛰고** 병원 정보 동기화는 그대로 진행한다.
- **voice의 실제 IP는 여기 없다.** 구급차 노트북마다 네트워크가 달라 자주 바뀌므로,
  voice가 뜰 때 자기 IP를 탐지해 hub에 직접 자가등록한다. info는 포트만 알려준다.
- GPS는 대회 데모 단계라 서울 랜드마크로 고정한 값(실시간 아님).

### 7.4 ③ hub → info : `HospitalBedUpdate` (병상 부분 갱신)

`POST /hub/bed-update` (info 포트 **5002 고정**, 팀 합의)

```json
{
  "hospitalId": "S0000001",
  "availableBedCount": 11,
  "status": "confirmed",
  "updatedAt": "2026-08-13T01:20:00Z",
  "source": "rule"
}
```

- **왜 필요한가**: `send_to_hub.py`의 주기적 재조회(기본 30분)만으로는 이송 확정 시점에
  바로 반영이 안 되어, 그 사이 **같은 병상에 다른 구급차가 중복 매칭**될 수 있다.
- **처리**: `SupabaseEgenClient.update_bed_count()`로 `hvec` 컬럼에 즉시 반영.
  실제 Supabase 병상이 줄어드는 것까지 검증 완료.
- **다른 필드를 담지 않는 이유**: name/gps/nightDutyAvailable/specialties는 hub가 바꿀
  이유가 없다. 받는 쪽은 `hospitalId`로 찾아 `availableBedCount`만 덮어쓰면 된다.
- info 서버가 잠깐 안 떠 있어도 hub는 예외를 흡수하고 계속 진행하며, hub 쪽에
  재시도 큐(`pending_bed_updates.jsonl`)가 있다.

### 7.5 ④ hub → info : 거절 로그 (`POST /hub/rejection`)

**info 쪽 수신구는 이미 완성돼 있다. hub는 보내기만 하면 된다.**

받는 쪽 원칙은 **관대하게 받는다**이다. 여기서 까다롭게 굴면 저쪽이 못 붙이고, 그 사이
로그는 **영영 사라진다**(소급 생성 불가).

```jsonc
// 지금 hub가 dashboard에서 받는 거절 액션을 그대로 전달해도 기록된다
{"action": "hospital_reject", "hospital_id": "A1100026", "timestamp": "..."}

// 나중에 이유가 붙으면
{"caseId": "case-abc", "hospitalId": "A1100026", "diseaseGroup": "중증화상",
 "reasonCode": "ON_CALL_MISMATCH", "declaredAtRequest": "Y", "timestamp": "..."}
```

- **필수는 `hospitalId` 하나뿐**(`hospital_id`/`hpid` 표기도 받는다). 이유가 없으면
  `UNSPECIFIED`로 기록.
- **모르는 필드는 버리지 않고 `extra`에 보존**한다 — 나중에 스키마가 바뀌어도 그 사이
  로그가 죽지 않게. 스냅샷에 가공 전 원본을 남기는 것과 같은 이유다.
- 한 건 또는 배열 모두 받는다. 날짜별 JSONL에 append-only로 쌓인다.

**거절 이유 어휘 (4축)** — `python -m hospital_score.rejection --vocab`

| 축 | 이유 코드 | 무엇을 갱신하나 |
|---|---|---|
| 구조적 | `NO_WARD` `NO_DEPARTMENT` `NO_EQUIPMENT` | 역량 벡터를 수정. **E-Gen 신고가 틀렸다는 증거** |
| 주기적 | `ON_CALL_MISMATCH` `NIGHT_UNAVAILABLE` | 시간대·요일 패턴. 상수 점수에 반영하면 안 됨 |
| 순간적 | `BEDS_FULL` `OR_OCCUPIED` `STAFF_BUSY` | 그때의 여건. 병원 속성이 아님 |
| 환자 요인 | `SEVERITY_EXCEEDED` `AGE_LIMIT` | 병원 속성이 아니라 환자-병원 조합 |
| 미분류 | `NO_RESPONSE` `UNSPECIFIED` `OTHER` | — |

**왜 4축으로 나누나**: 이유 없이 거절 횟수만 세면 화상 병동이 아예 없어서 거절한 것과
그날 당직이 정형외과라서 거절한 것이 한 덩어리가 된다. 그러면 **일시적 사정 때문에 그
병원을 영구히 후보에서 밀어내게 된다** — 뺑뺑이를 줄이려다 선택지를 좁히는 결과다.

**두 개의 파생 지표**

- `declaredAtRequest`(물어볼 당시 E-Gen 신고값)를 같이 받으면 **"가능이라 신고했는데
  거절"**을 셀 수 있다 → 신고 정확도를 운영 데이터로 **직접 측정**.
- 구조적 거절이 반복되는 병원 = **신고 오류 후보** 목록이 자동으로 나온다.

**⚠️ 편향 주의 — `NO_RESPONSE`를 반드시 남길 것.** 거절 로그는 **우리가 후보로 올린
병원에서만** 생긴다. 점수가 낮아 후보에 못 든 병원은 영원히 데이터가 안 쌓이고,
**낮은 점수가 낮은 점수를 재생산하는 되먹임**이 생긴다. 한 번 낮게 평가된 병원은
반증할 기회조차 갖지 못한다.

### 7.6 ⑤ (제안) `assessment` — `HospitalInfo`의 superset

기존 `HospitalInfo`에 **`assessment` 키 하나만** 얹는다. 기존 필드는 그대로다.

```jsonc
{
  "hospitalId": "A1100038", "name": "…", "gps": {…},   // ← 기존 필드 전부 그대로
  "availableBedCount": 30, "bedsByType": {…}, "capabilities": […],

  "assessment": {
    "assessedAt": "2026-08-13T01:20:00+09:00",
    "source": "rule",
    "conditions": {
      "availableBeds": 30, "totalBeds": 146, "bedOccupancy": 0.795,
      "overcrowded": false, "bedCountUnknown": false,
      "feedAgeMinutes": 3539915, "stale": true, "missingFromFeed": false
    },
    "evidence": { "designatedFields": ["화상"], "specialists": {…}, … },
    "groups": {
      "중증화상": {
        "status": "unknown",
        "tier": "unknown_designated",
        "score": 0.8,
        "confidence": "medium",
        "basis": [
          "병원 신고 없음(정보미제공)",
          "전문병원 지정: 화상",
          "마지막 입력 2458일 전",
          "등급: 응급실운영신고기관"
        ],
        "items": { "19": "정보미제공" }
      }
      // … 15그룹
    }
  }
}
```

**크기**: 병원당 약 5.1KB, 533곳 전체 약 2.2MB.
실제 객체는 `python -m hospital_score.scoring --payload 한강성심`으로 찍어볼 수 있다.

**hub가 쓰는 방법 (권장)**

1. 예상 병명 → 15그룹 중 하나로 매핑 (기존 임베딩 매칭 그대로)
2. 그 그룹의 `score`(0.2~1.0)와 거리 점수를 **hub가 정한 비중으로** 합산
3. `confidence`는 **점수에 곱하지 말고** 화면에 그대로 표시
4. `status`가 `unavailable`이어도 **후보에서 제거하지 말고 아래로 내릴 것**
5. `basis`를 dashboard에 그대로 노출 — "왜 이 병원인가"의 답이다

**⚠️ 이름 충돌 주의**: 기존 `capabilities`는 역량 코드 7종 `list[str]`이고, 판정의
15그룹은 `assessment.groups`다. 서로 다른 것이라 네임스페이스를 분리했다.

## 8. hub와 합의된 변경사항과 후속 작업

> 2026-08-13, info가 요청한 사항을 **hub 쪽에서 수정하기로 합의**됐다.
> 아래는 합의 내용과 그에 따라 각 브랜치가 해야 할 일이다.

### 8.1 🔴 hub로 흐르는 병원을 7곳 → 533곳으로

**문제**

```
E-Gen 실 API   533곳
   ↓  send_to_hub.py  _remap_to_supabase_hpid()   ← 대응표에 없으면 전부 버림
hub              7곳
```

`SUPABASE_TO_EGEN_HPID` 대응표 밖의 기관을 전부 버려서, E-Gen에서 533곳을 받아도
hub에는 7곳만 간다. **원인은 병상을 Supabase에서 읽는 구조**다(§3.3).

실제 영향:
- 존(Zone)을 넓혀도 전국에 후보가 **7곳뿐**
- 그 7곳은 **전부 서울** — 지방 이송은 후보 **0곳**
- 뺑뺑이 방지가 목적인데 선택지가 7개

**합의된 해법: 병상 차감을 Supabase가 아니라 짧은 TTL 오버레이로 관리**

```
병상 = E-Gen 실값 + (확정된 차감 오버레이, TTL 10~15분)
   → Supabase 의존 제거 → 대응표 불필요 → 533곳 전부 hub로
```

**근거**: `hvidate` 갱신 경과 **중앙값 5분**(443곳 중 88.7%가 10분 이내). E-Gen은 실제로
계속 갱신된다. 그렇다면 "info 재조회(30분) 때 우리 차감이 리셋된다"는 기존 설계 전제를
다시 봐야 한다 — 낡은 값으로 되돌아가는 게 아니라 **병원이 직접 갱신한 진짜 값으로
바뀌는 것**이라, 오히려 우리 차감이 그걸 덮고 있으면 더 부정확하다. 이송 ETA가 10분인데
차감을 30분 유지하는 것도 과하다.

**딸려오는 변경 — 확인 필요**

| 영향 | 내용 |
|---|---|
| `hospitalId` 체계 | `S0000001`~`S0000007` → **실 hpid(`A1100017` 등)** |
| dashboard | 병원 대시보드가 `?id=`로 라우팅하므로 **라우팅 확인 필요** |
| hub `GET /identity` | 신원 조회 대상 id가 바뀜 |
| info 후속 작업 | `_remap_to_supabase_hpid()` 제거, `fetch_hospitals()`에서 병상도 실 API로 |

### 8.2 🔴 거절 사유 수집 시작

- **hub**: 거절 액션을 `POST /hub/rejection`으로 중계만 하면 된다. **스키마를 안 바꿔도
  오늘 당장 연동된다** (필수 필드 `hospitalId` 하나).
- **dashboard**: "수용 불가" 버튼에 사유 선택 추가. 어휘는
  `python -m hospital_score.rejection --vocab`
- **가능하면 함께**: `declaredAtRequest`, `caseId`, `diseaseGroup`, `NO_RESPONSE`

**늦어질수록 손해다.** 로그는 소급해서 만들 수 없다.

### 8.3 🟡 `assessment` 필드 수용

- hub의 pydantic이 unknown 필드를 거부하면 보내는 순간 기존 연동이 깨지므로
  **info 혼자 배포할 수 없고 hub와 동시에 가야 한다.**
- `schema.py`는 `extra="forbid"`인 팀 합의 계약 파일이라 필드 추가에 합의가 필요하다.
- **info 후속 작업**: 현재 `scoring.build_payload()`는 CLI 데모 경로에서만 호출된다.
  상시 파이프라인(`send_to_hub.py`)에 배선하는 작업이 남아 있다 —
  `fetch_hospitals()` 결과에 `score_hospital()` 결과를 얹어 보내면 된다.

### 8.4 🟡 stale 표시

전국 **25곳**이 하루 넘게 방치된 병상 값을 실시간처럼 송출 중이고 최고 **8.6년**이다.
**전국 가용병상 1위가 2,457일 묵은 값**이며, 2위부터는 전부 10분 이내 갱신이라 오염된
건 정확히 정렬 맨 윗칸 하나다.

hub가 `availableBedCount`로 순위를 매기기 시작하면 즉시 문제가 된다.
`assessment.conditions.stale` / `feedAgeMinutes`로 이미 실어 보낼 수 있다.

> **hub에 확인 요청**: 현재 hub가 `availableBedCount`를 필터에도 스코어링에도 쓰지 않는
> 것으로 보이는데, 맞는지 확인 부탁드립니다(hub 코드가 이 브랜치에 없어 직접 확인 불가).

### 8.5 🟢 dashboard 표시 규약

- `bedCountUnknown: true`면 "0"이나 "병상 없음"이 아니라 **"미상"**으로 (기존 규약 재확인)
- `assessment.groups[*].basis`를 그대로 노출 — "왜 이 병원인가"의 답이자 구급대원의 판단 근거
- `confidence`를 점수와 **별도로** 표시 — 섞으면 "확실히 낮음"과 "모르겠음"이 구분되지 않음


### 9.4 ⚠️ 새 장비에서 반드시 먼저 돌릴 것

심평원 수집 결과는 `data/` 아래라 **커밋되지 않는다.** 캐시가 없어도 점수는 나오지만
**심평원 근거가 통째로 빠져 미상이 전부 `unknown_bare`로 떨어지고**, 홀드아웃 검증
(화상 0→4)도 재현되지 않는다.

```bash
cd info/Hospital_inform/info
python -m hospital_score.hira_files --fetch    # 전문병원 지정 (API 2회)
python -m hospital_score.hira --build-join     # 조인 + 전문의 수 (API 약 520회)
```

### 9.5 격리 원칙

- `hospital_score/`는 **바깥 모듈을 import 하지 않고, 바깥에서도 이 폴더를 import 하지
  않는다.** 폴더째 지워도 기존 경로가 멀쩡하다(검증 전까지 버릴 수 있어야 하므로).
  유일한 예외는 CLI 데모용 지연 import 한 곳.
- `simulation/`은 `ocr/`을 가져다 쓰기만 한다. 반대 방향 의존은 없다.
- `schema.py`는 저장소의 아무 모듈도 import 하지 않는다(hub 계약 파일이므로).

## 10. 한계 · 폐기 판정 · 남은 결정거리

### 10.1 알려진 한계 (코드 주석에 명시)

1. **`ITEM_TO_DEPARTMENTS`(항목→진료과)는 외부 근거로 검증되지 않았다.** 우리가 세운
   표이고, 심평원 진료과가 대분류만 와서 특정성이 낮다.
2. **전문병원 지정 매칭은 하한이다.** 좌표가 없어 기관명으로만 붙으므로 표기 차이로 놓친다.
3. **`Y` 신고 자체의 정확도는 검증되지 않았다.** tier 5는 병원 말을 그대로 믿는 것이고,
   그게 맞는지는 운영 거절 로그가 쌓여야 안다.
4. **점수는 최신 프레임 하나만 본다.** 시계열을 쌓고 있지만 아직 `stale`/`feedAgeMinutes`로
   신선도만 반영한다.
5. **재현율(OCR)을 아직 못 쟀다.** 근거 통과율은 쟀지만 "원문에 있는데 안 뽑은 값"은
   사람이 만든 정답지가 있어야 센다.

### 10.2 폐기 판정 (되살리지 말 것)

이 트랙은 **만들기 전에 만들 가치가 있는지 숫자로 먼저 판정**한다.
아래 두 판정은 `python -m hospital_score.discarded`로 재현된다 (API 호출 0회).

| 안 | 죽은 이유 |
|---|---|
| **병상 수 예측 모델** | `P(만실 전환) = 0.568%` (95% CI 0.41~0.78%, 서울 6,519쌍·10분 지평 / 전국 50,133쌍은 0.301%) — 사전 등록 기준 2% 미달. 병상은 움직이지만 0까지 가는 일이 거의 없어 예측의 최대 이득이 모델 오차보다 작다 |
| **미상 칸 추정 모델** | 관측 3,574칸 중 **95.6%가 "가능"**(서울 표본은 97.3%) → 상수 기준선이 이미 95점. 라벨이 상위 등급에 편중된 **MNAR**이라 미신고 병원에 적용하면 **"미신고 병원도 대부분 수용 가능"**이라는 **위험한 방향**의 오류가 난다 |
| 병상 미상 보간 | 미상이 서울 55곳 중 0~1곳 — 문제 크기가 사실상 0 |
| 도착 시점 병상 예측 | `hvidate` 갱신 중앙값 5분, 88.7%가 10분 이내 — 메울 공백이 없음 |
| 중증도별 재실시간(LOS) 추정 | 정답(실제 체류시간)을 관측할 방법이 없음 |
| OCR 병원 특화도 프로파일 | 심평원이 이미 제공 + 실제 병원 서류를 구할 수 없음 |

**MNAR의 크기 (전국, 라벨이 어디서 나오는가)**

| 등급 | 명부 점유율 | 라벨 점유율 | 과대표집 | 그 등급의 가능률 |
|---|---|---|---|---|
| 권역응급의료센터 | 8.3% | 27.1% | **3.3배** | 94.8% |
| 지역응급의료센터 | 26.1% | 51.1% | 2.0배 | 97.3% |
| 지역응급의료기관 | 43.9% | 21.1% | 0.5배 | 92.2% |
| 응급실운영신고기관 | 21.8% | **0.7%** | **0.0배** | 100.0% |

**명부의 21.8%를 차지하는 최하위 등급이 라벨의 0.7%만 내놓는다.** 학습할 라벨은 신고를
성실히 하는 상위 등급에서 나오는데, 채우려는 미상 칸은 정반대쪽에 몰려 있다. 이것이
"추정 대신 계층"을 택한 직접적인 이유다.

> **재현성에 대한 기록.** 최초 분석(2026-08-11)은 `0.618%` / `4,215칸 중 97.0%`를 적었으나
> 그 계산 코드가 저장소에 없었다. 관측치(미상률·방치 병원·조인율·신선도)는 `report.py`로
> 전부 재현되는 반면 이 두 판정만 근거가 문서에만 있었다 — 이 보고서가 내건 기준에 미달하는
> 상태였다. 2026-08-14에 `discarded.py`를 추가해 재계산했고, `P(만실 전환)`은 **신뢰구간이
> 겹쳐 교차검증**됐다(0.618% ↔ 0.568%). 가능률도 97.0% ↔ 97.3%로 일치했다. 다만 `4,215칸`은
> 어느 표본 조합으로도 재현되지 않아(집계 단위 상이) 재현되는 값으로 교체했다.

> 그래서 경로 C의 목적은 **"미상 칸을 추정해 채우는 것"이 아니라 "신고와 대조해 어긋나는
> 지점을 드러내는 것"**으로 확정됐다.

### 10.3 남은 결정거리

- **명부에만 있는 90곳** — 병상 응답에 없어 `HospitalInfo`가 아예 안 만들어진다.
  hub 입장에선 존재하지 않는 병원이다. 좌표는 목록정보에 있으니 "병상 미상"으로 보낼 수
  있으나 `mapper.py` 변경이라 기존 경로에 영향이 간다.
- **`dutyEmclsName`(응급의료기관 등급)을 파이프라인에 태울지** — 목록정보에 이미 오는데
  아무 데도 안 쓰인다. 신고 성실도를 거의 그대로 설명한다(미상률 21.4% → 96.4%).
- **과밀 노출** — 지금 과밀(`-24` 등)은 `0`으로 낮춰 보내 "확인된 만실"과 구분되지 않는다.
  `availableBedCount`가 `ge=0`이라 노출하려면 스키마 필드 추가가 필요하다.
- **경로 B 합류 지점** — `DocumentFields` → `HospitalInfo` 병합. 서류는 정적이라
  좌표·실시간 병상은 건드리지 않고 E-Gen이 못 채우는 당직·인력만 덮어야 한다.
  값의 출처(AI/규칙) 표기 방식도 미정.
- **`requirements.txt`의 `Flask-SocketIO`** — `POST /hub/bed-update`가 순수 REST라
  실제로는 안 쓰인다. 제거 검토 필요.

### 10.4 유지보수 주의

- **`SUPABASE_TO_EGEN_HPID` 대응표는 수기 관리다.** Supabase 병원 구성이 바뀌면 같이
  갱신해야 한다. 안 맞으면 해당 병원은 병상만 있고 목록·중증질환 정보가 없는 상태로
  빠진다(`skipped_no_location`으로 리포트에 이름이 남는다).
  → **§8.1 합의가 적용되면 이 표 자체가 사라진다.**
- **표준 어휘가 두 벌 있다.** `schema.py`가 원본, `ocr/.../vocabulary.py`가 복사본이다.
  두 경로의 의존성을 갈라 두려고 일부러 복사했으며,
  `python ocr/scripts/run_extract.py --check-vocabulary`로 어긋났는지 확인한다.
- **CLAUDE.md 명세 오류 정정 필요** — `hv1`·`hv2`를 별도 API로 적고 있으나 실제로는
  가용병상 응답 **안의 필드**다(각각 응급실 일반병상 수, 내과 중환자실 병상 수).
  호출 설계 자체가 달라진다.

## 부록 — 설계 원칙 요약

이 브랜치의 코드 전반을 관통하는 규칙들이다. 새 기능을 붙일 때 이 목록과 어긋나지
않는지 먼저 본다.

1. **"모름"과 "없음"을 절대 섞지 않는다.** `0`(확인된 만실) / `키 없음`(미상) /
   `missingFromFeed`(응답에 없음) / `[]`(읽었는데 없다)를 전부 구분한다. 섞이면 사후에
   데이터 품질 문제인지 실제 상태인지 알 수 없고, 병합할 때 **모르는 값이 없는 값을 덮는다.**
2. **점수와 신뢰도를 곱하지 않는다.** "확실히 낮음"과 "모르겠음"은 다른 정보다.
3. **애매하면 후보에 남긴다.** 받을 수 있는 병원을 빼는 비용 ≫ 못 받는 병원을 올리는 비용.
4. **가공 전 원본을 보존한다.** 해석이 바뀌어도 과거 데이터를 다시 해석할 수 있어야 한다.
   실패 기록도 남긴다("데이터 없음" ≠ "호출 실패").
5. **받는 쪽은 관대하게, 만드는 쪽은 엄격하게.** 거절 로그는 필드 이름이 달라도 받고,
   `HospitalInfo`는 오타 하나에 즉시 실패한다.
6. **절대값·비중은 정보를 가진 쪽이 정한다.** info는 순서와 근거만, 거리와의 합산은 hub가.
7. **외부 재료가 빠져도 멈추지 않는다.** 근거가 약해질 뿐 프로세스는 계속 돈다.
8. **근거 없이 숫자를 만들지 않는다.** 만들기 전에 만들 가치가 있는지 숫자로 먼저 판정하고,
   미달이면 접는다(사전 등록 기준).
9. **모델/API 호출부와 판단 로직을 분리한다.** 소스가 셋(fixture/Supabase/HTTP)이어도
   매퍼는 하나다.
10. **격리 가능하게 만든다.** 검증 안 된 트랙은 폴더째 지워도 기존 경로가 멀쩡해야 한다.
