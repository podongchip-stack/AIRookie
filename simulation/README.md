# 시뮬레이션 GUI — 서류 인식 과정을 눈으로 본다

병원 서류(PDF·이미지)를 창에 끌어놓으면 영역을 나눠 읽고 필드를 뽑는 과정이
진행 중에 화면에 그려진다. 결과는 CLI(`ocr/scripts/run_extract.py`)와 같다.
다른 것은 **과정이 보인다**는 점뿐이다.

```
서류 끌어놓기
  → [규칙] 페이지 렌더링      PDF → 이미지 (pypdfium2, 200dpi)   ┐ simulation
  → [AI]  레이아웃 검출       영역 위치 + 종류 10종 분류          │
  → [규칙] 정리·라우팅        중복 제거 → 읽기 순서 → 태스크 배분  │ goldenlink_ocr
  → [AI]  영역별 인식         표는 표 모드로, 본문은 OCR 모드로    │
  → [AI]  필드 추출           그룹별 4회 호출, 스키마 제약 디코딩   ┐
  → [규칙] 근거 대조          원문에 없는 값은 버린다               │ goldenlink_extract
  → 표에 표시                 버려진 값도 남긴다                   ┘
```

CLI로 돌리면 이 과정이 텍스트 몇 줄로 지나가고 최종 JSON만 남는다. 그러면
**어느 영역을 어떤 태스크로 읽었는지**, **어떤 값이 어떤 근거로 기각됐는지**를
파일을 열어 대조해야 안다. 그 대조 작업을 화면이 대신한다.

## 화면

```
┌ PDF 또는 이미지를 창 안에 끌어놓으세요      [Ollama|Stub] [dpi] [파일 선택…] ┐
├──────────────────────────────┬──────────────────────────────────────────────┤
│ 페이지 미리보기                │ 진행                                        │
│  · 영역 박스 + 번호            │  [AI]   레이아웃 검출 — 영역 6개             │
│    회색 대기 → 초록 읽음        │  [규칙] 정리·라우팅 — 5개 (OCR 4, Table 1)   │
│    주황 검토 필요              │  [AI]   인식 1/5 · title — ○○대학교병원…    │
│  · 박스를 누르면 그 영역 텍스트  │  [AI]   필드 추출 3/4 · 진료과·인력 — 호출   │
│                              │  [규칙] 근거 대조 — 채택 4, 버림 1           │
├──────────────────────────────┴──────────────────────────────────────────────┤
│ 추출 필드   필드 │ 값(AI 제안) │ 근거 원문(AI) │ 판정(규칙)                    │
│  specialties[0].doctorCount │ 7 │ "흉부외과 2명" │ 버림 — 근거에 값 7이 없다   │
└─────────────────────────────────────────────────────────────────────────────┘
```

`[AI]`는 값을 **찾는** 단계, `[규칙]`은 그 값을 **받아들일지 정하는** 단계다
(CLAUDE.md 핵심 AI 활용 원칙). 표에서 기각된 값은 빨간 글씨로 남는다 —
무엇을 뽑았는지보다 **무엇을 왜 버렸는지**가 이 모듈의 확인 대상이기 때문이다.

## 셋업

[`ocr/`](../ocr/README.md)이 먼저 돌아가는 상태여야 한다. 이 폴더는 그 위에 창만 얹는다.

```bat
:: 1) OCR·추출 의존성 — GPU 필요
pip install torch --index-url https://download.pytorch.org/whl/cu128
pip install -r ocr\requirements.txt -r ocr\requirements-extract.txt
python ocr\scripts\download_models.py

:: 2) GUI 의존성
pip install -r simulation\requirements.txt

:: 3) 실제 추출까지 보려면 (Stub 모드로는 불필요)
ollama pull qwen3:14b
ollama serve
```

| 패키지 | 버전 | 라이선스 | 용도 |
|---|---|---|---|
| `tkinterdnd2` | 0.6.2 | MIT | 창에 파일 끌어놓기 |
| `pypdfium2` | 5.12.1 | BSD-3-Clause / Apache-2.0 택일 | PDF 페이지 → 이미지 |

`tkinter`는 파이썬에 들어 있어 설치 대상이 아니다.

**PyMuPDF를 쓰지 않은 이유는 라이선스다.** PDF 렌더링에 가장 흔히 쓰이지만
AGPL-3.0이라, 레이아웃 모델을 ONNX로 바꿔가며 AGPL 전염을 피한 결정
(`ocr/README.md` "레이아웃 모델을 ONNX로 쓰는 이유")과 정면으로 충돌한다.
pypdfium2와 내부 PDFium은 그 문제가 없다.

## 실행

```bat
conda activate ml
cd C:\Dev\Project\AIRookie
python simulation\gui.py
```

- 상단 **Stub**을 고르면 Ollama·GPU 없이도 전 과정이 돈다 (필드 값은 가짜지만
  근거 대조·어휘 검증 로직은 실제로 동작한다). 화면과 로직을 확인할 때 쓴다
- **Ollama**를 고르면 실제 추출이 돈다. Ollama 서버가 떠 있어야 한다
- 결과 JSON은 CLI와 같은 자리(`ocr/output/`)에 같은 규칙
  (`YYYYMMDD_HHMMSS_문서명.json`, 덮어쓰지 않음)으로 쌓인다. 파일명 규칙은
  `run_extract.py`의 것을 그대로 가져다 쓴다 — 두 경로가 갈라지면 안 되기 때문
- 여러 장짜리 PDF는 **페이지마다 별도 문서**로 처리한다 (`문서명_p1`, `문서명_p2`…).
  추출기가 문서 1건 단위이기도 하고, 당직표 여러 장이 묶인 PDF는 장마다 기준일이
  다를 수 있다

## 성능 (실측)

RTX 5080 / 합성 A4 서류 2페이지(제목 + 6행 표 + 본문 2줄), 200dpi, 페이지당 영역 4개.

| 단계 | 시간 | 비고 |
|---|---|---|
| PDF 렌더링 | 0.04s/장 | 200dpi A4 → 1653×2339px |
| OCR 모델 로드 | 3.0s | **처음 한 번만.** 이후 서류를 연달아 넣어도 재사용 |
| 영역 인식 | 2.2~2.5s/영역 | 페이지당 8.6~10.1s (영역 4개) |
| 필드 추출 (Stub) | 0.00s | LLM 호출이 없다 |
| 필드 추출 (Ollama) | **미측정** | 문서 1장당 4회 호출 |

GPU 점유는 OCR 모델 상주 상태에서 3.0GB였다(다른 프로그램 점유 포함). LLM까지
같이 올리면 [`ocr/README.md`](../ocr/README.md)의 "동시 상주 — VRAM 배분" 표를 따른다.

> **이 숫자로 하면 안 되는 판단이 있다.** 합성 문서라 글자가 깨끗하고 영역이
> 4개뿐이다. 실물 서류는 영역이 10~20개로 늘고 팩스본은 더 걸린다. 재현율·정확도는
> 여기서 잰 것이 하나도 없다 — 그 숫자는 [`ocr/README.md`](../ocr/README.md)의
> 실측 표를 봐야 한다.
> 모델 로드 3초도 OS 파일 캐시가 더워진 상태의 값이라, 부팅 후 첫 실행은 더 걸린다.

## 구조

```
simulation/
├── README.md          이 문서 — 화면 · 셋업 · 성능 실측 · 한계
├── requirements.txt   tkinterdnd2 · pypdfium2 (OCR 의존성 위에 얹는다)
├── gui.py             화면 — 끌어놓기 수신, 미리보기·영역 박스,        [Tk]
│                      진행 로그, 필드 표. 위젯을 만지는 곳은
│                      큐를 비우는 _drain() 경로뿐이다
├── runner.py          워커 스레드 — 렌더링→OCR→추출을 순서대로 돌리고
│                      진행 이벤트를 큐에 넣는다. 모델은 한 번만 올려 재사용
└── pdf.py             PDF 페이지 → PIL 이미지 (제너레이터, pypdfium2)
```

`[Tk]` 표시가 있는 파일만 위젯을 만진다. 나머지 둘은 화면을 몰라서, 창 없이
불러다 쓰거나 테스트할 수 있다.

### 왜 스레드를 나눴는가

Tk 위젯은 메인 스레드에서만 건드릴 수 있는데 서류 한 장 읽는 데 10초 안팎이
걸린다. 메인 스레드에서 돌리면 창이 통째로 얼어 죽은 것과 구분되지 않는다.
그래서 처리는 워커 스레드에서 하고 화면으로는 **큐를 통해서만** 건넨다.

`runner.py`에 `tkinter` import가 하나도 없는 것이 그 경계다. 여기서 위젯을 만지는
코드가 생기면 import 줄이 먼저 눈에 띈다.

### `ocr/`에서 무엇을 바꿨는가

두 곳에 선택적 진행 콜백(`on_progress`)만 추가했다. 기본값이 `None`이라 기존
CLI 동작은 그대로다.

| 파일 | 이벤트 |
|---|---|
| `goldenlink_ocr/pipeline.py` | `detect`[AI] → `route`[규칙] → `recognize`[AI] ×N |
| `goldenlink_extract/extractor.py` | `group_start`[AI] / `group_done`[규칙] / `group_failed` ×4 |

콜백은 파이프라인과 같은 스레드에서 불리고 예외를 던지면 처리가 그 자리에서
멈춘다. 그래서 GUI는 큐에 넣기만 한다.

## 한계

- **한 번에 한 건.** 처리 중에 새 파일을 놓으면 무시하고 로그에만 남긴다
- **PDF 지원은 이 폴더 안에만 있다.** `run_extract.py --image`는 여전히 이미지만
  받는다. CLI에도 필요해지면 `pdf.py`를 `goldenlink_ocr`로 옮기는 편이 맞다
- 결과를 화면에서 **고칠 수 없다.** CLAUDE.md가 말하는 Override(구급대원이 AI
  산출물을 확인·수정)는 dashboard의 몫이고, 여기는 확인까지만 한다
- 앞에 다른 바이트가 붙은 변종 PDF는 이미지로 잘못 넘어간다. 그 경우 PIL이 열지
  못해 오류로 드러나므로 조용히 틀린 결과가 나오지는 않는다
- 데모·검증용이다. 이 창을 통해 병원 서류를 정식으로 처리하는 경로가 아니다
